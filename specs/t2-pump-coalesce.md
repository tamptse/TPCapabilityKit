## Problem Statement

Every scheduling entry pumps the pending path with its own unstructured concurrent task: the fire-and-forget schedule entry, the schedule-and-wait entry, and the settlement retry re-queue each spawn an independent drain. A burst of N schedules therefore spawns N concurrent drains that all dequeue from the same priority order, contend on the one scheduler lock for dequeue plus park plus activation-gate transitions, and park or activate the same rows through interleaved paths. Most of the drains find an empty queue and exit, so the work is pure overhead: task allocation plus lock contention plus duplicate empty-drain iterations, scaling with burst size rather than with real work. The retry re-pump joins the same herd from inside settlement, so a flaky burst multiplies it.

## Solution

Coalesce the three kick sites into one pump: entries only enqueue through the lifecycle table and then kick a single drainer, which runs alone per scheduler generation while activation work stays concurrent. A drain-in-flight flag (or equivalent controlled-drain guard) owned beside the lifecycle table decides: kick when idle starts one drain, kick while draining returns immediately because the running drain will observe the newly enqueued row on its next dequeue. The drain loop decouples fast dequeue from slow activation — it dequeues rapidly in order and hands each available row to concurrent activation while parked rows keep their existing waiter path — so throughput and parallelism are unchanged and only the duplicate-drain overhead disappears. No behavior change except coalescing: same dequeue order, same park reachability, same activation gate, same settlement and retry identity, same counts.

## User Stories

1. As a Tasks maintainer, I want one drain in flight per scheduler instead of one per entry, so that I stop auditing N interleaved dequeue loops to answer one drain question.
2. As a burst scheduler, I want N rapid schedules to enqueue N rows with at most one running drain, so that lock contention and empty-drain iterations stop scaling with burst size.
3. As a schedule-and-wait caller, I want my enqueue to kick the same shared pump as fire-and-forget, so that both entries behave identically under burst.
4. As a retry integrator, I want settlement retry re-queue to kick the same shared pump, so that flaky-then-recovered work rejoins the one drain instead of spawning a rival one.
5. As a priority consumer, I want dequeue order (priority first, FIFO within priority) identical before and after, so that high-before-low pins keep passing unchanged.
6. As a slot operator, I want activation concurrency unchanged (available rows still activate concurrently under scoped-hold admission), so that global and per-capability limits plus FIFO wake behave exactly as today.
7. As a parked waiter, I want unavailable rows to park exactly once through the single park seam with wake-clear and terminal-take-and-cancel untouched, so that capability arrival still wakes to activation.
8. As a cancel caller, I want cancel-while-queued, cancel-while-parked, and cancel-while-active to land terminal exactly as today, so that no cancel is lost across the fused kick.
9. As a reentrant kick, I want a kick arriving from inside the drain (retry settle during activation) to be observed without deadlock or missed wakeup, so that the re-queued row is always drained.
10. As a cancelled pump, I want pump-task cancellation to clear the drain flag and re-kick when work remains, so that cancellation never strands a non-empty queue behind a stuck flag.
11. As a generations reader, I want the drain flag scoped per scheduler generation with slot admission still shared across live generations, so that reconfigure keeps draining the old generation while new work enters the new one.
12. As a counts reader, I want pending/active/drained counts to agree exactly as today through the single snapshot, so that prune and drain detection need no re-audit.
13. As a Deadline consumer, I want expiry resolution and the single waiter-vs-execution race untouched, so that timeout behavior is identical before and after.
14. As a settlement reviewer, I want the single terminal decision plus waiter preservation plus scope-exit release untouched, so that this candidate extends single-settlement instead of reopening it.
15. As a test author, I want coalescing proven by behavior through the public schedule/cancel/wait seam, so that the pump is verified by outcomes not by flag spelling — except one mechanical check proving no entry spawns a raw drain directly.
16. As a future contributor, I want one kick entry to call instead of three raw spawns, so that no second pump protocol can be re-introduced by a new entry.
17. As an ADR reader, I want the change traceable to unified lifecycle ownership, single-settlement, single park seam, and scoped-hold decisions, so that the coalescing clearly respects prior decisions rather than reopening them.
18. As a Bridge consumer, I want wait-then-run delivery and timeout behavior identical before and after, so that this refactor stays invisible from Objective-C.

## Implementation Decisions

- **Module**: Tasks remains the deep module behind the schedule/cancel/pending/active seam. The lifecycle table (or its owning scheduler beside it) gains one pump guard: a drain-in-flight flag plus a kick entry plus the drain loop. No new module is introduced.
- **Interface**: the public scheduling seam is unchanged (schedule/schedule-and-wait/cancel/pending/active plus result rendezvous plus counts). The internal change is three raw drain spawns collapse into one kick entry: each site enqueues through its existing table transition, delivers displaced payloads and slot evict exactly as today outside the lock, then calls kick instead of spawning a drain.
- **Drain-vs-activation split**: the drain loop must decouple fast dequeue from slow activation. Dequeue stays a rapid locked step in priority order; each dequeued available row is handed to concurrent activation (child work sharing the existing activation gate, scoped hold, Deadline race, and settlement) while the drain continues dequeuing instead of awaiting each activation serially. A strictly serial await-inside-loop shape is rejected: it would introduce head-of-line blocking where the second available row waits for the first execution to finish, collapsing configured parallelism and breaking slot serialization pins.
- **Kick semantics**: kick is enqueue-then-kick, never kick-then-enqueue. Under the one scheduler lock it checks the drain flag: idle sets draining and starts one drain task; already-draining returns immediately with no new task. The flag check and set share one locked step so two racing kicks cannot both start a drain.
- **Missed-wakeup guard**: the drain clears the flag only after observing an empty queue, in one locked clear-plus-recheck step. Work enqueued between the last dequeue and the flag clear is therefore either observed by the recheck (drain continues without clearing) or lands after the clear with its own kick starting a fresh drain (kick sees idle). No enqueue is ever left behind an idle flag.
- **Reentrancy**: kicks from inside the drain (settlement retry during a concurrent activation) follow the same already-draining fast path. Correctness rests on the missed-wakeup guard, not on recursion: the running drain's next dequeue observes the re-queued row because retry re-enqueues through the table before kicking.
- **Cancellation**: the drain task clears the flag in a scope-exit step even when cancelled, and re-kicks when the queue is non-empty after cancel. Activation work keeps its existing cancellable waits (slot-hold cancel, Deadline race, registry wait); pump cancellation never cancels in-flight activations, it only ends the dequeue loop.
- **Lock discipline**: the flag transitions hold the one scheduler lock once and never nest. Table transitions, park factory invocation (non-suspending), slot evict, waiter delivery, continuation resume, expiry race, registry wait, and slot hold stay outside the flag step exactly as today. The park waiter factory rule (must not suspend under lock) is unchanged.
- **Generations**: the flag is per scheduler generation, matching the existing per-generation lifecycle table. Counts still sum across live generations while slot admission shares the one Store-owned domain; reconfigure still lets the old generation drain naturally while new work enters the new one. No cross-generation pump coordination is introduced.
- **Seam**: the highest seam stays the Tasks schedule/cancel/pending/active facade plus the single result rendezvous, the registry whole-set wait, and the counts snapshot. Tests cross that seam; no new seam is created. The lifecycle table remains the single writer: each Lease mutation happens together with its row write in one locked transition.
- **Expand–contract**: add the kick-plus-guarded-drain beside the three existing raw spawns, migrate the three kick sites one by one, then delete the raw-spawn spelling. No flag-window dual behavior beyond the migration ticket; CI stays green batch to batch because the old form still exists until the migrate ticket lands.
- **Depth**: depth decreases by two caller-visible drain protocols (three spawns to one kick). No new abstraction is added; the guard is one flag plus one entry beside the existing table, not a new pump layer.
- **Locality**: enqueue, kick, dequeue, and missed-wakeup recheck share one reviewable block with the single transition, so the burst path needs no hop across three call sites to audit.
- **Leverage**: leverage is herd removal plus drift removal: one drain to audit, one kick for future entries, zero duplicate empty drains under burst. Risk is bounded because the move is kick-plus-flag only — same rows, same places, same order index, same snapshot derivation, same activation and settlement paths — only the drain multiplicity changes.
- **Respects ADRs**: single-settlement path constrains outcome, delivery, and release to stay untouched; unified lifecycle ownership requires the table (not callers) to own row transitions; single park-seam discipline forbids moving park or waiter lifetime into the pump; single scoped-hold discipline forbids moving admission or release into the drain loop.

## Testing Decisions

- A good test crosses the public Tasks seam (schedule/schedule-and-wait/cancel/pending/active) and asserts externally observable behavior (burst drains to zero with every completion delivered exactly once; priority high-before-low preserved; slot limits serialize with FIFO wake; retry re-pump recovers through the same drain; cancel-while-queued/parked/active lands terminal), never the spelling of the flag or the absence of the raw spawns as an implementation detail — except one mechanical check proving no entry spawns a raw drain directly.
- Modules under test: kick guard (second kick while draining starts no second drain; kick after drain-idle starts one; enqueue-between-last-dequeue-and-clear is never stranded), drain loop (rapid dequeue preserves priority order; available rows activate concurrently under slot limits; parked rows park once and wake to activation), retry interplay (retry re-queue during drain is observed without an extra drain).
- Prior art: scheduler suites (retry recovery through the facade, cancel-while-parked landing terminal), lifecycle suites (double-park plus counts, terminal removal plus same-id reschedule, retry restores pending), determinism suites (virtual-time timeout, cancel-pins-expired, priority high-before-low, slot serialization), activation-gate and slot-hold suites (admission refusal, TOCTOU re-check, FIFO wake, cancellable wait), same-identity exchange pins (concurrent schedule-wait storm resolves exactly once). The coalescing must keep every one green with zero test-semantics edits.
- Verification per ticket: build green plus full test suite green; raw drain spawns shrink monotonically (present beside the new kick after fuse, absent after migrate, unreferenced after pin).

## Out of Scope

- Any change to lifecycle reachability, priority ordering, retry budget or void-completion policy, waiter preservation or exactly-once delivery, slot limits or release ownership (stays with activation scope-exit), expiry resolution (task timeout vs configured default), or time adapters.
- Changing the public lease shape, the typed-optional wait signatures, the Bridge live-view reflection, state creation/observation, registry emission order or lock discipline, generation prune or shared-slot coupling, or deterministic-time spelling.
- Touching the park capability-waiter primitive, the slot evict primitive, Deadline internals, the registry wait implementation, or the activation gate beyond its existing call site.
- Reopening single-settlement, unified-lifecycle-ownership, single-rendezvous, scoped-hold, or same-identity policy decisions: no revisit trigger is met; the coalescing extends them to the pump, it does not redesign them.
- Reformatting or renames beyond the coalescing.

## Further Notes

- Grill verdict (autonomous self-grill; decided, no questions asked):
  - T2-Q1 Ordering under concurrent drains — is order already safe today? Adopted: dequeue itself is atomic under the one lock so dequeue order is already priority-FIFO; the herd cost is contention plus duplicate empty drains, not misordering. The coalesced drain must preserve the same dequeue order verbatim, pinned by priority tests.
  - T2-Q2 Serial drain — can the drain simply await each activation? Adopted: no. Await-inside-loop serializes available rows behind the first execution and collapses configured parallelism (head-of-line blocking). The drain must hand available rows to concurrent activation and continue dequeuing; throughput pins (slot serialization, concurrent completion) prove it.
  - T2-Q3 Reentrant kick from retry — does already-draining drop it? Adopted: no, by the missed-wakeup guard. Retry re-enqueues before kicking, so the running drain's next dequeue (or its clear-plus-recheck) observes the row; the kick itself correctly does nothing when draining.
  - T2-Q4 Cancelled pump — can draining strand true? Adopted: scope-exit clear plus re-kick-on-nonempty removes the strand. Pump cancellation ends only the dequeue loop; in-flight activations keep their own cancellation paths untouched.
  - T2-Q5 Flag scope — one flag per scheduler or one global? Adopted: per scheduler generation, matching the per-generation table. Cross-generation coordination would couple prune with pumping for no gain; the shared slot domain already constrains admission globally.
  - T2-Q6 Is this a behavior change or pure coalescing? Adopted: pure coalescing. Same enqueued set, same order, same park/activate/settle paths, same counts; only drain multiplicity changes. Tests pin this by staying green with zero semantics edits plus new coalescing pins.
  - Rejected: serial-await drain (breaks parallelism), global cross-generation flag (couples prune to pumping), moving park or slot admission into the pump (violates untouched scope), deleting the recheck as redundant (reopens the missed-wakeup window).
- Deletion test is the acceptance bar: deleting the three raw drain spawns (callers read only the kick entry) changes nothing observable through the public seam.
- Source of prototype decisions: none — no prototype; decisions derive from the three-spawn inventory, the serial-await head-of-line analysis, and single-transition ownership decisions.
