## Problem Statement

Deterministic-time control is spelled three times across three hops for one virtual advance: the Store facade owns `enableDeterministicTime` / `advanceTime(by:)` / `waitForDeterministicWaiters(count:)` / `generationCount` as thin adapters with a fresh-instance precondition, `StoreSchedulingGenerations` re-spells the same three controls plus the precede-first-use gate (`generationCount == 0`) next to `current` / `reconfigure` / `snapshot` / `pending` / `active` / `prunedSnapshot`, and the time module re-spells them a third time as `Clock.enableDeterministic` / `advance(by:)` / `waitForWaiters(count:)` plus `VirtualTime.sleep` / `advance` / `awaitWaiterRegistered`. A reviewer asking "what must hold before I advance virtual time?" must hop facade precondition, generations gate, Clock adapter gate, and the `VirtualTime.advance`-implies-`awaitWaiterRegistered`-plus-poll/yield/1ms/5s-precondition chain to assemble one answer, and each hop is a drift risk: a fourth spelling of the fresh-instance rule, a gate that checks the wrong count, or a timing-policy tweak applied on one side only. The sum-vs-share split (snapshot sums pending/active across live generations while slot admission shares one Store-owned domain so reconfigure never doubles the limit during drain) is stated once in a comment but enforced across three modules, so a future reader cannot tell which seam owns the invariant.

## Solution

Keep the shared slot-domain plus shared-clock wiring exactly as it is (ADR-0021 load-bearing) but delete one delegation layer: expose the deterministic controls on `StoreSchedulingGenerations` only, with the Store facade keeping `configure` / `cancel` / `pending` / `active` while tests cross the narrower generations seam instead of the facade for time. The alternative considered is moving the precede-first-use gate into `Clock.enableDeterministic` so Generations stops counting to guard time; the tie-break prefers facade-trim because the gate reads naturally next to the pruned count it guards, while the Clock stays a pure adapter. Document the sum-vs-share split as a single snapshot postcondition test rather than a comment. No behavior change: enable-once, virtual-only advance, waiter rendezvous, shared slot domain, shared clock across generations, and prune-then-loop snapshot arithmetic are identical before and after. This spec is SPECULATIVE per ADR-0026: do not implement until the revisit trigger fires (see Further Notes) and N5 has landed (same `DynamicStore.swift` file).

## Implementation Decisions

- **Module**: `StoreSchedulingGenerations` becomes the single owner of deterministic-time spelling (enable/advance/wait plus the precede-first-use gate); the Store facade loses its three time forwarders but keeps production scheduling (`configureScheduler`, `scheduleTask`, `scheduleTaskAndWait`, `cancelTask`, `pendingTaskCount`, `activeTaskCount`); the time module (`Clock` / `VirtualTime`) is untouched except for caller updates. No new module is introduced; one delegation layer is deleted.
- **Interface**: the public scheduling seam is unchanged for production callers. The deterministic seam narrows from facade-level (`enableDeterministicTime` / `advanceTime` / `waitForDeterministicWaiters`) to generations-level; test-only callers cross the narrower seam. The fresh-instance precondition (never on `DynamicStore.shared`) travels with whichever seam keeps guarding tests, stated once, not twice.
- **Depth**: depth decreases by one delegation layer (facade forwarder deleted). No new abstraction is added; the generations gate plus the pruned-count read stay adjacent in the same function, and the `Clock` adapter gate stays where it is. The alternative (gate moves into `Clock.enableDeterministic`, Generations drops its count check) is rejected at rest for the reason in Further Notes but may be revived if the trigger review prefers it.
- **Seam**: the highest time seam becomes the generations deterministic interface. Tests cross that seam; no new seam is created and no test touches `Clock` or `VirtualTime` directly. The snapshot (`pending` / `active` / `generationCount`) remains the one generations read tests assert through.
- **Adapter**: no adapter change. Live/virtual adapters plus the advance policy stay behind the one sleep seam in the time module per ADR-0023; the single shared time instance across generations is preserved so reconfigure never forks virtual time.
- **Locality**: the precede-first-use check, the pruned generation count, the enable-once swap, and the virtual-only advance/wait gates sit in two adjacent places at most (gate beside count in Generations; adapter gates inside `Clock`), so the full "what must hold before advance" path reads without hopping facade → generations → clock → virtual policy.
- **Leverage**: leverage is delegation deletion plus invariant promotion (comment → postcondition test): one gate to audit, one timing policy to extend, one snapshot test to guard sum-vs-share. Risk is bounded because the change is spelling-only — every forwarder body today is a single call — but churn risk is real while prune logic settles, which is why the spec is gated speculative.
- **Respects ADRs**: ADR-0021 (shared slot domain across generations; reconfigure never doubles the limit during drain) forbids any admission-domain change — the trim touches spelling only; ADR-0023 (time module owns live/virtual adapters plus advance policy behind one sleep seam; one shared time instance; Store keeps thin spelling-only delegation — this change narrows that delegation deliberately without moving adapter policy outward); ADR-0026 (facade split parked; deterministic-time spelling stays on the facade to avoid churning the test surface; revisit only on fourth lock domain, renewed friction, or stable prune — this spec fires only on that trigger); ADR-0022 (Store→Tasks lock order) requires prune-then-loop and emission discipline to stay verbatim.

## Testing Decisions

- A good test crosses the generations deterministic seam (or the facade production seam for counts) and asserts externally observable behavior (enable before first schedule succeeds; enable after first schedule traps; advance expires exactly the due waiters once; wait-for-waiters rendezvous synchronizes without a second policy spelling; snapshot sums pending/active across two live generations during drain while admission still enforces one shared limit; reconfigure never forks virtual time), never the spelling of the deleted forwarder — except one mechanical grep proving no facade time forwarder remains.
- Modules under test: generations deterministic controls (enable gate, advance delegation, waiter rendezvous), snapshot postcondition (sum pending/active, share slot domain, prune drained, `generationCount` agrees), time module untouched behavior (enable-once, virtual-only advance/wait, advance wakes only expired exactly once).
- Prior art: deterministic-time suites around enable-precedes-first-use, advance/wait rendezvous, and reconfigure-drain count suites around pending/active aggregation plus shared-limit admission; the trim must keep every one green with test-seam updates only (facade-time call sites re-pointed to generations), zero behavior-semantics edits, plus one new snapshot postcondition test promoting the sum-vs-share comment to code.

## Out of Scope

- Any change to time semantics (enable-once, virtual-only advance/wait, advance-wakes-only-expired exactly once, poll/yield/1ms/5s rendezvous values, non-negative advance, shared clock across generations).
- Any change to slot admission (shared Store-owned domain, scoped hold, FIFO wake, cancellable wait, scope-exit release) or snapshot arithmetic (prune-then-loop, sum across live, drain naturally).
- Touching State creation/observation, capability registry emission or whole-set wait, lifecycle/settlement, Deadline timeout-once resolution, Bridge mapping, or lease identity.
- Introducing a scheduler protocol, new public API, new lock domain, per-generation clocks, or per-generation slot isolation.
- Renames beyond the trim or formatting churn.
