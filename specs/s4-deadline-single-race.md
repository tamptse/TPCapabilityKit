## Problem Statement

A Tasks maintainer asking "which race owns expiry?" gets two answers in the same expiry module: a `Bool` race for the capability wait and a value-carrying race for the executor, each with its own TaskGroup topology (one operation task plus one sleep task, first-wins, cancel-all). The two topologies drifted because the value generalization landed as expand-then-migrate with no contract step: the value form was added beside the `Bool` form, the executor migrated off the side-channel holder, and both races stayed. Reviewers must now audit two first-wins blocks plus a double-optional decode split across two sites — the flow unwraps the outer optional (timeout vs won) while the Settlement step applies the void-completion policy to the inner value (stored-nil vs never-stored) — to answer one expiry question the glossary already promises has one answer: one race shared by waiter and executor, timeout resolved once at construction.

## Solution

Keep the named expiry type with resolve-once construction and unify it behind one value-carrying race: a single private TaskGroup topology is the only place that races an operation against the sleep seam, the value form is the canonical spelling, and the `Bool` wait is a thin mapping over it (timeout maps to `false`) applied at the registry seam. The double-optional decode collapses to the settlement site so the won gate and the void-completion policy read as one truth table adjacent to the decide-then-transition block. No behavior change: resolve-once, single shared expiry, expiry-wins with late-loser discard, waiter preservation, retry identity, and the registry never naming the expiry type are identical before and after.

## Implementation Decisions

- **Module**: Tasks remains the deep module behind the schedule/cancel/pending/active seam. The expiry module keeps owning timeout-once resolution plus the single race; the time module keeps owning live plus virtual adapters and the advance policy behind one sleep seam. No new module is introduced; unification removes duplication inside the existing expiry module.
- **Interface**: the value-carrying form becomes canonical (timeout as `nil` outer vs won as `.some(value)` where value may itself be `nil`); the `Bool` form becomes a thin mapping over it (timeout maps to `false`) applied where the flow adapts to the registry-owned race value. The named type, its construction from task plus configured default, and its readable resolved timeout are kept untouched so the contract suite keeps constructing it directly; the keep-named decision is honored and the collapse alternative stays out of scope.
- **Depth**: depth decreases by one duplicated topology with zero new abstraction. The single private TaskGroup shape (one operation task plus one sleep task, first-wins, cancel-all, loser discarded never stored) is stated once; both public forms share it and only the carried payload mapping differs.
- **Seam**: the highest seams stay the Tasks schedule/cancel/pending/active facade plus the single result rendezvous and the registry whole-set wait (which keeps its `Bool`-race value parameter). Tests cross those seams; no new seam is created. The registry never names the expiry type — the flow adapts the `Bool` mapping into the existing closure value exactly as today.
- **Adapter**: no adapter change. The Bridge live Lease view, ObjC timeout mapping (wire-negative vs explicit plus pinned-compat literal), and time live/virtual adapters plus advance policy are untouched; deterministic-time spelling stays on the facade.
- **Locality**: the double-optional decode collapses to the settlement site. The flow passes the raced outcome into the settlement entry without unwrapping; the won gate (timeout path never consults the carried value) and the void-completion policy (nil result with budget retries; nil without budget fails when active else expires) read as one truth table adjacent to the single decide-then-transition block. A bare-optional fold without the won gate is rejected, and the budget/policy ownership stays in Settlement, never in the flow or the Lease.
- **Expiry-wins**: first-wins plus cancel-all stays the topology; expiry-wins means the timeout outcome dominates once taken — the late loser value is discarded by cancellation and, even if it arrives, never consults into an already-expired Lease because the won gate plus single terminal transition refuse it. No tie-break priority is added; ties remain first-completed-wins, which the deterministic suites already pin by behavior.
- **Ordering**: unification lands after the value-migration post-state and before any future address change. It assumes the terminal-unify and slot-eviction-unify post-state and must not re-split what they fused. The keep-named decision is a precondition, not a follow-up.
- **Respects ADRs**: one-waiter-with-injectable-clock constrains the change to keep one resolved timeout feeding both paths deterministically; expiry-ownership (resolve-once plus single race for wait and execution) is fulfilled rather than reopened — unification is the missing contract step that makes "single race" literally true; single-expiry-clock constrains the work to keep the one sleep seam and idempotent release discipline with no second clock and no second holder.

## Testing Decisions

- A good test pins externally observable behavior through the public Tasks seam with deterministic time (expired vs completed vs retry, delivered value identity, waiter counts, park-expires-once, mid-wait flip wins, late-loser discarded, already-satisfied fast path), never the topology spelling or holder internals — except mechanical greps proving one TaskGroup site in the expiry module and one outer-optional decode site at settlement.
- Modules under test: race parity (`Bool` mapping: operation-win `true` vs timeout `false` vs operation-`false`; value form: won-with-value vs won-with-stored-nil vs timeout-empty), executor path (race-carried value into Settlement, timeout delivering expired with empty result, stored-nil retry vs fail vs expire truth table), registry wait (empty-set true, already-satisfied true, whole-set win vs single-expiry timeout, per-Capability-before-snapshot order untouched), resolve-once construction (nil resolves to default, explicit travels unchanged, ObjC wire-negative resolves to default, omitted pins compat literal).
- Prior art: resolve-once construction suite, execution-expiry delivery, operation-wins race, single-expiry waiter-plus-executor agreement, timeout-contract shared-expiry across mid-wait flip, value-carries-value proofs (value win, stored-nil retry/recovery, stored-nil without budget, timeout-empty, late-loser discard, parked-once, flip win, fast path), registry wait suites, Settlement and Settlement-guards (void-completion retry policy), activation-gate and slot-hold suites. The unification must keep every one green with zero test-semantics edits.

## Out of Scope

- Deleting, privatizing, or renaming the named expiry type (keep-named is honored; the collapse alternative stays closed).
- Any change to timeout resolution (task value vs configured default), the pinned-compat timeout fork, or the sleep seam and advance policy.
- Any change to the Settlement decision table, retry budget, void policy outcomes, waiter preservation, exactly-once delivery, or slot-release ownership (stays with activation scope-exit).
- Any change to lifecycle reachability, priority ordering, park double-park or waiter-cancel rules, generation sharing, or State creation/observation.
- Changing the registry wait interface shape, emission order, or lock discipline; generalizing the registry seam beyond `Bool`.
- Splitting the Store facade, introducing a scheduler protocol, adding a lock domain, or any formatting churn beyond the race unification plus decode collapse.

## Further Notes

- Deletion/duplication test is the acceptance bar: removing either public race form's private topology (both read the one shared block) breaks compilation, and a search for the TaskGroup construction in the expiry module returns exactly one site at rest; a search for the outer-optional unwrap returns exactly one site at the settlement entry.
- If mapping-direction is contested during implementation, prefer value-canonical with `Bool` as the thin map (not `Bool`-canonical with value built on top), because the executor's `Any?` payload is the load-bearing case and the waiter's `true`/`false` folds trivially onto won/timeout without a new type.
- If outer-optional vs result-enum is contested, prefer the outer-optional (timeout `nil` outer, won `.some(value)`) over a new result enum, because it adds zero named types and the won gate already exists at the settle entry — but either is acceptable iff the stored-nil vs never-stored truth table is preserved and asserted by test.
- Source of decisions: no prototype; decisions derive from the two-race plus two-decode-site inventory, the whole-set wait seam inventory, ADRs for one waiter, expiry ownership, and single expiry, plus the value-migration history below.

Auto-deepened: ticket-01 is that missing contract step; acceptance is one TaskGroup site, not a third form.
