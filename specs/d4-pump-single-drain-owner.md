## Problem Statement

The pump coalescing work gave the scheduler one drain at a time, but the drain lifecycle still reads as three scattered pieces: a drain-in-flight flag checked-and-set beside the lifecycle table at kick time, plus two separate queue-nonempty rechecks — one on the normal loop tail and one on the scope-exit path that also covers cancellation. A reviewer answering "when does a drain own the queue, when does it hand over, and when does a kick start a fresh drain versus return immediately" must hold all three sites in mind at once, because the flag and the queue count are never observed as one lifecycle. The settlement-to-drained signal the generation reaper needs has the same problem: the only drain-stability reader is the reaping pass itself, with no settle/drain notification that reconfigure and settle points can call, so the planned move of reaping off the read path has no seam to build on.

## Solution

Give the pump one reviewable drain lifecycle owned beside the lifecycle table: a single drain owner holding the idle/draining state with one kick entry, one finish-or-continue rule shared by the loop tail and the scope-exit path, and one settle/drain notification callable from reconfigure and settle points. The drain still constructs one expiry race per dequeue and threads it through park and activation unchanged; dequeue order, park reachability, the activation gate, settlement identity, and counts derivation are untouched. Non-current generations drain monotonically is re-proven under coalesced pumping so the reaper's trust-the-flag sweep stays sound, and the provided contracts hand D1 and D3 a stable kick shape plus an explicit notification to build on.

## User Stories

1. As a Tasks maintainer, I want one drain owner to read instead of a flag plus two rechecks, so that kick, drain, handover, and rekick answer in one reviewable block.
2. As a burst scheduler, I want N rapid schedules to enqueue N rows with at most one running drain, so that lock contention and empty-drain iterations never scale with burst size.
3. As a schedule-and-wait caller, I want my enqueue to kick the same single entry as fire-and-forget, so that both entries behave identically under burst.
4. As a retry integrator, I want settlement retry re-queue to kick the same single entry, so that flaky-then-recovered work rejoins the running drain instead of spawning a rival one.
5. As a priority consumer, I want dequeue order (priority first, FIFO within priority) identical before and after, so that high-before-low behavior never shifts.
6. As a slot operator, I want activation concurrency unchanged (available rows still activate concurrently under scoped-hold admission), so that global and per-capability limits plus FIFO wake behave exactly as today.
7. As a parked waiter, I want unavailable rows to park exactly once through the single park seam with wake-clear and terminal-take-and-cancel untouched, so that capability arrival still wakes to activation.
8. As a cancel caller, I want cancel-while-queued, cancel-while-parked, and cancel-while-active to land terminal exactly as today, so that no cancel is lost across the unified lifecycle.
9. As a reentrant kick, I want a kick arriving from inside the drain (retry settle during activation) to be observed without deadlock or missed wakeup, so that the re-queued row is always drained.
10. As a cancelled pump, I want pump-task cancellation to clear the drain ownership and re-kick when work remains, so that cancellation never strands a non-empty queue behind stuck ownership.
11. As a generations reader, I want the drain ownership scoped per scheduler generation with slot admission still shared across live generations, so that reconfigure keeps draining the old generation while new work enters the new one.
12. As a counts reader, I want pending/active/drained counts to agree exactly as today through the single snapshot, so that drain detection needs no re-audit.
13. As a Deadline consumer, I want expiry resolution and the single waiter-vs-execution race untouched, so that timeout behavior is identical before and after.
14. As a settlement reviewer, I want the single terminal decision plus waiter preservation plus scope-exit release untouched, so that this candidate extends single-settlement instead of reopening it.
15. As a reconfigure caller, I want a settle/drain notification I can call at explicit reconfigure and settle points, so that drained generations can release without any getter triggering the reap.
16. As a D1 implementer, I want one drain owner with a single kick entry whose shape stays stable for settle-retry repump callers, so that my work builds on a fixed entry instead of chasing kick spellings.
17. As a D3 implementer, I want the non-current-generations-drain-monotonically invariant re-proven under coalesced pumping, so that trusting the drained flag at sweep time stays sound.
18. As a test author, I want single-ownership proven by behavior through the public schedule/cancel/wait seam, so that the lifecycle is verified by outcomes (at most one drain, no stranded enqueue, notification fires on settle-to-drained) not by ownership spelling.
19. As a future contributor, I want exactly one kick entry and one notification to call, so that no second pump or reap-trigger protocol can be re-introduced by a new entry.
20. As an ADR reader, I want the change traceable to unified lifecycle ownership, single-settlement, single park seam, scoped-hold, and Store-to-Tasks lock order decisions, so that the lifecycle clearly respects prior decisions rather than reopening them.
21. As a Bridge consumer, I want wait-then-run delivery and timeout behavior identical before and after, so that this refactor stays invisible from Objective-C.

## Implementation Decisions

- **Module**: Tasks remains the deep module behind the schedule/cancel/pending/active seam. The single drain owner (idle/draining state plus kick entry plus finish-or-continue rule plus settle/drain notification) lives beside the lifecycle table in the owning scheduler. No new module is introduced.
- **Interface**: the public scheduling seam is unchanged (schedule/schedule-and-wait/cancel/pending/active plus result rendezvous plus counts). Internally, all kick sites read only the single kick entry, and reconfigure/settle points read only the settle/drain notification. The kick entry shape stays stable for settle-retry repump callers.
- **Drain-owner collapse shape**: adopted — one owner holds the drain state and observes queue-emptiness with it in a single locked step, instead of a bare flag beside the table plus two independent count rechecks. The lifecycle table stays the single row writer; counts derivation (single immutable snapshot) is untouched. Decision shape:
  - states: idle vs draining, with exactly one owned handover (clear-plus-observe) shared by every exit.
  - rejected: keeping the bare flag plus two count reads (the status quo split this candidate removes), and fusing drain state into the row table itself (would move pump ownership into the single-writer table and reopen unified-lifecycle-ownership).
- **Rekick rule**: adopted — defer-tail vs loop-tail unified into one finish-or-continue rule spelled once and shared by the loop tail and the scope-exit path. The normal empty observation continues the loop or clears-and-exits through the same predicate the scope-exit uses to clear-and-rekick on cancellation; work enqueued between the last dequeue and the handover is either observed by the shared rule (drain continues) or lands after handover with its own kick starting a fresh drain. Decision shape:
  - rule: nonempty queue means continue-or-rekick, empty queue means clear-and-exit, evaluated once per handover with no second spelling.
  - rejected: defer-only (leaves the normal tail without an explicit continue) and loop-tail-only (leaves cancellation without a re-kick), plus deleting either recheck as redundant (reopens the missed-wakeup window).
- **Notification shape**: adopted — a single void settle/drain hook invoked outside the scheduler lock after terminal settlement lands a generation drained, and callable from explicit reconfigure points. The Store subscribes without the scheduler lock held, preserving the Store-to-Tasks lock order; the drained predicate itself (empty pending plus active from one acquisition) is unchanged, only the wakeup becomes explicit so getters can later stop triggering the reap. Decision shape:
  - hook: fire-and-forget void signal carrying at most generation identity, never row payloads, never invoked under lock.
  - rejected: a delegate protocol (new protocol seam for a void signal; variation stays via values, not protocols), and pure generation polling with no push (gives D1 no explicit trigger and keeps the read-path coupling this unblocks removing).
- **Race threading**: the drain constructs one expiry race per dequeue and passes it as a value to park and activation; the race constructor and value form stay exactly as the race-interface owner defines them. This candidate threads the race through unchanged and never names or reshapes the race type.
- **Generations**: ownership is per scheduler generation, matching the per-generation table. Counts still sum across live generations while slot admission shares the one Store-owned domain; reconfigure still lets the old generation drain naturally while new work enters the new one. The re-proven invariant: non-current generations drain monotonically (new work lands only on current, cancel only removes, retry re-queues within its own generation), so a flagged-drained generation cannot become live before the sweep and the sweep needs no drain re-check under its own lock.
- **Seam**: the highest seam stays the Tasks schedule/cancel/pending/active facade plus the single result rendezvous, the registry whole-set wait, and the counts snapshot, with the settle/drain notification as the one added wakeup. Tests cross that seam plus the notification; no new test-only seam is created.
- **Expand–contract**: add the unified owner plus notification beside the existing flag spelling, migrate the kick and handover sites onto the single rule one by one, then delete the split spelling. No dual-behavior window beyond the migration ticket; the suite stays green batch to batch.
- **Depth**: depth decreases by one caller-visible lifecycle protocol (flag-plus-two-rechecks to one owner with one rule). No new abstraction layer is added; the owner is one state plus one entry beside the existing table.
- **Locality**: kick, handover, finish-or-continue, and notification share one reviewable block with the single row transition, so the burst path plus the drain-stability question need no hop across kick, tail, scope-exit, and reaper to audit.
- **Leverage**: leverage is audit collapse plus unblock: one lifecycle to review, one kick plus one notification for D1/D3 to build on, zero split-recheck drift. Risk is bounded because the move is ownership-plus-wakeup only — same rows, same places, same order, same park/activate/settle paths, same snapshot — only the lifecycle spelling and the explicit signal change.
- **Respects ADRs**: single-settlement path constrains outcome, delivery, and release to stay untouched; unified lifecycle ownership requires the table (not callers) to own row transitions with the owner beside it owning only drain state; single park-seam discipline forbids moving park or waiter lifetime into the owner; single scoped-hold discipline forbids moving admission or release into the drain loop; Store-to-Tasks lock order forbids invoking the notification under the scheduler lock or re-checking drain state under the sweep lock.

## Testing Decisions

- A good test crosses the public Tasks seam (schedule/schedule-and-wait/cancel/pending/active) plus the settle/drain notification and asserts externally observable behavior (burst drains to zero with every completion delivered exactly once; at most one drain runs under burst and reentrancy; enqueue between last dequeue and handover is never stranded; notification fires when settlement lands a generation drained; priority high-before-low preserved; slot limits serialize with FIFO wake; retry re-pump recovers through the same drain; cancel-while-queued/parked/active lands terminal), never the spelling of the owner or the hook as an implementation detail — except mechanical checks proving a single kick entry and a single handover rule.
- Modules under test: drain owner (second kick while draining starts no second drain; kick after idle starts one; handover never strands; cancel clears ownership with re-kick on nonempty), notification (terminal settle to drained fires exactly once per transition outside the lock; reconfigure point can trigger the same release path), generations (non-current drained flag never flips back live under burst plus cancel plus retry; sweep removes only still-present non-current flagged generations, never current).
- Prior art: the burst-coalescing, reentrancy, and ordering pins (at most one drain, retry observed without an extra drain, priority order, cancel pins) stay green with zero semantics edits; scheduler suites (retry recovery through the facade, cancel-while-parked landing terminal), lifecycle suites (double-park plus counts, terminal removal plus same-id reschedule, retry restores pending), determinism suites (virtual-time timeout, cancel-pins-expired, priority high-before-low, slot serialization), activation-gate and slot-hold suites (admission refusal, TOCTOU re-check, FIFO wake, cancellable wait), same-identity exchange pins, and the named-reap pass suites (copy-check-sweep, current-never-reaped, flagged-drained removal).
- Verification per ticket: build green plus full test suite green; split-lifecycle spellings shrink monotonically (flag-plus-two-rechecks beside the owner after introduction, absent after migration, unreferenced after pinning).

## Out of Scope

- Any change to lifecycle reachability, priority ordering, retry budget or void-completion policy, waiter preservation or exactly-once delivery, slot limits or release ownership (stays with activation scope-exit), expiry resolution (task timeout vs configured default), or time adapters.
- Moving the reap off the read path (belongs to D1), getter-purity changes, generation prune policy changes, or the generations snapshot sum-vs-share split.
- Changing the public lease shape, the typed-optional wait signatures, the Bridge live-view reflection, state creation/observation, registry emission order or lock discipline, or deterministic-time spelling.
- Touching the park capability-waiter primitive, the slot evict primitive, race internals, the registry wait implementation, or the activation gate beyond its existing call site.
- Reopening single-settlement, unified-lifecycle-ownership, single-rendezvous, scoped-hold, same-identity, generations-snapshot, slot-sharing, or Store-to-Tasks lock-order decisions: no revisit trigger is met; the lifecycle extends them, it does not redesign them.
- Reformatting or renames beyond the single-owner plus notification.

## Further Notes

- Dependency: **blocked-by D7 race interface contract**. Ticket 01 carries the hard blocked-by edge: it must not land until the race-interface owner confirms the race constructor and value form are stable, because the unified drain constructs one race per dequeue and passes it to park and activation. Assumed stable interface: task-plus-default-plus-clock construction with a value-form race the registry receives without naming the race type. If D7 reshapes construction or the value form, this candidate re-threads but does not redesign. Tickets 02 and 03 inherit the edge transitively through 01.
- Provided contracts for D1/D3 implementers:
  - (a) One drain owner with a single kick entry: every enqueue-then-kick site (fire-and-forget, schedule-and-wait parked branch, settlement retry re-queue) calls the one entry; the entry shape stays stable for settle-retry repump callers; at most one drain runs per generation.
  - (b) A settle/drain notification callable from reconfigure and settle points: void hook fired outside the scheduler lock when terminal settlement lands a generation drained, plus callable from explicit reconfigure points, carrying at most generation identity so D1 can relocate the reap off getters onto explicit passes.
  - (c) Re-proven non-current-generations-drain-monotonically invariant under coalesced pumping: schedule lands only on current, cancel only removes, retry re-queues within its own generation — so a flagged-drained non-current generation cannot become live before the sweep and the sweep needs no drain re-check under its own lock. D3 builds prune/drain separation on this proof.
- Self-grill verdict (autonomous self-grill; decided, no questions asked):
  - D4-Q1 Flag-plus-count collapse shape — keep the bare flag, fuse into the row table, or add one owner beside the table? Adopted one owner beside the table holding idle/draining plus the single handover. The bare flag keeps two truths apart across three sites; fusing into the row table drags pump state into the single-writer table and reopens ownership.
  - D4-Q2 Rekick rule — defer-tail only, loop-tail only, or one shared rule? Adopted one finish-or-continue rule shared by both exits. Either tail alone leaves one exit (normal or cancelled) without an explicit handover, and deleting a recheck reopens the missed-wakeup window T2 closed.
  - D4-Q3 Notification shape — delegate protocol, bare generation poll, or void closure hook? Adopted void closure hook fired outside the lock at settle-to-drained plus reconfigure points. A delegate adds a protocol seam for a void signal; polling gives D1 no explicit trigger and preserves the getter coupling being removed.
  - D4-Q4 Does the owner touch park, activation, settlement, or slot admission? Adopted no. The owner moves only drain state and wakeup; park reachability, the activation gate, the terminal decision with waiter preservation, and scope-exit release stay byte-for-byte in behavior.
  - D4-Q5 Does notification fire under the scheduler lock or after unlock? Adopted after unlock, outside the lock, adjacent to waiter delivery. Firing under lock nests the Store-to-Tasks order the reaper just finished removing.
  - D4-Q6 Two tickets or three? Adopted three (unify owner, add notification, re-prove plus pin) in expand–contract order, so the lifecycle collapse lands independently reviewable from the new wakeup and the invariant proof is a reviewable artifact D3 can cite.
  - Rejected: serial-await drain (breaks parallelism, already rejected), global cross-generation ownership (couples prune to pumping), moving park or slot admission into the owner (violates untouched scope), delegate-protocol notification (leverage ~nil), deleting either recheck as redundant (reopens missed wakeup), firing notification under lock (reintroduces lock nesting).
