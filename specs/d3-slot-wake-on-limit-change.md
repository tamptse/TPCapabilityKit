## Problem Statement

The slot domain admits queued waiters only on scope-exit release: the limit entry mutates the two configured caps silently and wakes nobody. Behind one shared slot domain this is a limit-raise stall — a reconfigure that raises the global or per-capability headroom leaves fitting waiters parked until some unrelated holder happens to release, so newly configured capacity idles while queued demand waits for no reason related to its own fit. From a scheduler user's perspective, raising limits does nothing observable until churn happens elsewhere, and throughput after a raise tracks the next accidental release instead of the new configuration. Lowering limits is the symmetric hazard in reverse: any future wake-on-change that admits without re-checking the new caps would overshoot the freshly tightened bound. The consideration set (which waiters fit right now) is owned by exactly one path today — the release scan — and the limit entry does not cross it, so a reviewer asking "who reconsiders the queue when the caps move?" finds no seam to answer with.

## Solution

Deepen the limit change into a first-class wake event that reuses the same consideration path as release: the limit entry updates the caps and then crosses the identical scan-plus-install consideration (arrival-order first-fit FIFO with skip under one lock hold, admitted batch resumed outside the lock in arrival order) that release owns. Admission rules stay bit-identical — a skipped waiter keeps its place and is reconsidered on every later consideration, newcomers still park behind queued waiters, one consideration admits at most what the headroom allows and limits are never overshot — so the homogeneous case behaves exactly as before and only the raise stall changes. The slot domain self-wakes: the limit entry owns consideration plus batch resume inside the slot domain, while reconfigure keeps its shape (store the new configuration, thread the new caps into the shared domain, append a fresh generation, reap via the explicit point) with no new Tasks pump. The wake hooks into the explicit reconfigure/settle point the reap/settle owner names, never into a count-getter read, so reads stay reads. Scope-exit release stays the single release; the limit path installs holds but never releases one.

## User Stories

1. As a scheduler operator raising the global cap, I want queued waiters that now fit to activate on the reconfigure itself, so that new capacity flows immediately instead of waiting for an unrelated release.
2. As a scheduler operator raising a per-capability cap, I want every fitting waiter admitted in arrival order within the new headroom, so that disjoint demands unblock together instead of serializing across accidental releases.
3. As a scheduler operator lowering a cap, I want the change to admit nobody and overshoot nothing, so that tightening is provably safe without a special case at the call site.
4. As a scheduler operator applying a mixed change (one cap up, the other down), I want admission bounded by the new headroom on both axes, so that correctness needs no old-vs-new comparison math.
5. As a FIFO waiter whose demand fits the new caps, I want arrival order among fitting waiters preserved, so that fairness survives the new wake source.
6. As a skipped waiter whose demand still exceeds the new caps, I want my place kept and reconsideration on every later release and limit change, so that skipping delays but never strands me.
7. As a newcomer arriving while waiters are queued, I want to keep parking behind them even when headroom exists, so that the queued scan owns new capacity first from both wake directions.
8. As a global-limit operator, I want one limit change to admit at most the new global headroom, so that limits are never overshot by a wake batch.
9. As an unbounded-limit operator (nil cap), I want raises toward unbounded to drain every fitting waiter in order, so that removing a bound behaves like infinite headroom, not like one wake.
10. As a slot reviewer, I want one consideration path crossed by both release and limit change, so that capacity check plus install plus batch resume audits in a single hop instead of two scans that can drift.
11. As a scope-exit reviewer, I want release to stay the single release, so that limit wake installs holds but never picks a release site.
12. As a reconfigure integrator, I want reconfigure shape preserved (store configuration, thread caps, append generation, reap via the explicit point), so that in-flight drain behavior is untouched by the new wake.
13. As the reap/settle owner (D1 integrator), I want the wake reachable only via the explicit reconfigure/settle point, so that no count getter triggers consideration and reads stay pure.
14. As the drain owner (D4 integrator), I want woken waiters to cross the unchanged activation gate (terminal refusal returns its slot, availability re-check may fail, row activation may refuse), so that refusal cascades through the single release and the coalesced pump needs no rebase.
15. As a cancel caller, I want cancellable wait unchanged, so that a waiter cancelled mid-consideration still resolves false exactly once and never holds a scanned slot.
16. As a displacement integrator, I want stale-evict and self-cancel intents untouched, so that same-identity overwrite keeps settling first with slot-only eviction.
17. As a duplicate scheduler, I want duplicate rejection unchanged, so that an already-held or already-queued identity still refuses through the same atomic install.
18. As an activation-path reviewer, I want woken means admitted (slot already installed under the lock), so that no woken waiter ever re-parks and no wake-then-contend churn exists on either wake source.
19. As a test author, I want the raise stall pinned through the scheduling facade (blocked queue plus raised cap activates in order), so that the fix is proven by observable activation rather than queue spelling.
20. As a test author, I want the lower-is-no-op plus never-overshoot pins through the facade, so that tightening is proven safe by behavior, not by reading a guard.
21. As a test author, I want homogeneous FIFO order re-pinned unchanged, so that the shared scan cannot silently reorder waiters that all fit.
22. As a Bridge consumer, I want scheduling behavior identical from Objective-C, so that this wake stays invisible across the adapter.
23. As an ADR reader, I want the change traceable to scoped-hold ownership, the single release, the shared slot domain, first-fit FIFO with skip, and the explicit reap/settle point, so that the wake clearly extends prior decisions rather than reopening them.
24. As a future contributor, I want the raise-wakes / lower-no-ops / mixed-bounded-by-headroom policy plus the slot-self-wakes argument recorded once, so that a later reconfigure-pumps-Tasks rewrite must answer the lock-order evidence.

## Implementation Decisions

- **Module**: the slot controller remains the slot module owning admission, wake order, cancellable wait, waiter eviction, scope-exit release, and now limit-change consideration. Tasks keeps owning park, Deadline expiry, activation, and the Settlement step. The generations owner keeps owning configuration storage, generation append, and the explicit reap. No Lease or row logic moves into the controller; no new module is introduced.
- **Interface**: the scoped-hold seam stays the sole admission seam with its shape unchanged; the limit entry gains a wake obligation, not a new method or parameter. Callers learn one documented sentence (a limit change reconsiders the queue through the same first-fit FIFO-with-skip consideration; raises admit, lowers naturally admit none), not a second admission spelling. The rejected alternative (a scan-mode flag or a separate limit-wake entry with its own loop) would split one admission decision across two caller-visible spellings for zero gain.
- **Depth**: depth increases with no new seam: the same locked consideration that frees-then-finds on release now also finds on limit change, so both wake sources review as one scan. No new abstraction layer is added.
- **Seam**: the highest seam stays the scheduling facade (schedule/schedule-and-wait/cancel/pending/active plus configure) with the scoped-hold seam as the sole admission crossing. Behavior pins cross the facade; the shared consideration is pinned narrowly at the controller seam. No new seam is created, and no count getter becomes a wake seam.
- **Adapter**: no adapter change. The Bridge stays the single ObjC scheduling adapter and is untouched; limit wake is invisible from Objective-C.
- **Shared consideration**: one scan-plus-install path under one lock hold, crossed by both release and limit change (shared-consideration shape: update caps, then scan from the head admitting every fitting waiter via the atomic install, then resume the admitted batch outside the lock). A separate limit scan is rejected: it duplicates the capacity check plus install plus resume discipline and reopens the two-copy drift the eviction unify closed — a future fix would land in one scan and miss the other.
- **Wake trigger**: any limit change crosses the shared consideration; admission decides. Raise-only triggering is rejected: it needs old-vs-new comparison across two optional (nil-means-unbounded) caps plus mixed raise-one/lower-other math, for zero runtime gain — reconfigure is rare and the scan is linear in queue length. Lowers and shrunk axes naturally admit none because the atomic install enforces the new caps; the call site carries no raise-vs-lower branch.
- **Wake budget**: one limit change admits every fitting waiter in arrival order within the same locked pass, bounded by the new headroom — at most the new global headroom when a global cap binds, per-capability headroom otherwise. Single-wake-per-change is rejected: one raise can free several disjoint per-capability slots when no global cap binds, and single-wake would serialize disjoint demands for no fairness gain. Woken means admitted under the lock, so no woken waiter ever re-parks; the wake-then-contend alternative is rejected because it churns continuations for capacity never reserved.
- **Resume discipline**: admitted waiters resume outside the lock as an arrival-ordered batch on both wake sources, extending the existing no-reentrancy rule. Resuming continuations under the controller lock risks re-entrancy into park/cancel and is rejected on both paths.
- **Slot-self-wakes**: the limit entry owns consideration plus batch resume inside the slot domain (controller lock only). The reconfigure-pumps-Tasks alternative is rejected: driving Tasks activation from reconfigure would split admission across two modules, nest the generations lock across activation (violating the single Store-to-Tasks crossing the reap owner states once), and duplicate the release-adjacent scan beside the scoped-hold ownership. Reconfigure only threads the new caps and keeps its append-plus-reap shape.
- **Explicit-point hook**: the wake is reachable only via the explicit reconfigure/settle point the reap/settle owner names; no count or snapshot read triggers consideration. Getter-triggered wake is rejected: it reintroduces read-that-writes plus an unnamed lock crossing, the exact shape the count/prune separation exists to close — and it is the hard sequencing reason this work lands after that owner.
- **Reconfigure preservation**: reconfigure still stores the new configuration, threads the caps into the one Store-owned shared domain, appends a fresh generation, and reaps via the explicit point with identical drain and in-flight behavior. The sum-vs-share split (counts sum across live generations while admission shares one domain, so reconfigure never doubles the configured limit during drain) is stated once and untouched.
- **Park coherence**: the newcomer no-overtake rule is kept on both wake sources: a newcomer arriving while waiters are queued still parks even if it would fit, because the queued consideration owns new headroom first. Relaxing it for limit wake would let newcomers jump the queue the shared scan just made fair.
- **Activation interplay**: woken waiters cross the unchanged admission gate (terminal refusal returns silently, availability re-check may fail the lease, row activation may refuse a displaced row). Any refusal exits the hold scope and releases through the single scope-exit release, cascading into the next scan — throughput is preserved through refusal churn with no special path, and the coalesced pump observes only normal activation traffic.
- **Locality**: caps update, scan, capacity check, install, queue removal, and batch capture read adjacent inside the consideration step, so the full wake contract needs no hop. The raise-wakes/lower-no-ops policy note lives beside that step, not in callers.
- **Leverage**: leverage is stall removal at fixed interface cost: one consideration to audit, zero caller changes, zero new seams. Blast radius is bounded because the homogeneous-demand and lower-change cases behave exactly as before (scan admits in order or admits none) and only the heterogeneous raise stall changes.
- **Respects ADRs**: scoped-hold ownership (admission, wake order, cancellable wait, scope-exit release behind one seam — the consideration stays inside that ownership, the seam shape untouched); single scoped-hold seam (no second wake spelling); hold Lease-keyed with the newcomer-keyed retire exception (eviction intents untouched); task-keyed slot ownership with controller-owned idempotent release (consideration touches only caps plus queued waiters, never held entries); shared slot domain across generations (one Store-owned domain, reconfigure never doubles the limit during drain); first-fit FIFO with skip (scan restarts at the head on every consideration, skipped waiter loses no place, no overtake counter).

## Testing Decisions

- A good test pins externally observable activation order through the scheduling facade with cap moves (raise wakes a blocked head plus fitting followers in order; homogeneous FIFO order identical; lower-change admits nobody; mixed change admits only new headroom; limits never overshot; newcomer still parks behind queued waiters; gate-refused waiter returns its slot and the cascade continues) plus narrow controller pins of the shared consideration (first-satisfiable admitted, unsatisfiable head skipped without losing place, batch resumes all admitted outside the lock) — never the loop spelling, never which wake source admitted which waiter.
- Modules under test: the shared consideration (order plus headroom budget on both wake sources), the limit entry (raise admits, lower no-ops, mixed bounded), the explicit-point wiring (reconfigure shape preserved, no getter wakes), and the activation-gate interplay (refusal returns slot, cascade continues).
- Prior art: the slot-hold suite (double-acquire rejection, stale/self eviction pins, arrival-order log pin), the scoped slot suite (drain, cancel-during-acquire, injected-domain limits), the fair-wake HOL pins (blocked head plus fitting follower), the shared-slot-domain suites (reconfigure under pressure never doubles the limit), and the generations wiring suites are the models — all stay green with zero test-semantics edits. No existing test covers limit-raise wake (raising limits today wakes nobody by construction), so the raise pins are purely additive and nothing re-pins.
- Verification per ticket: `swift build` green plus full `swift test` green; grep confirms a single consideration spelling crossed by both wake sources, no getter-triggered consideration, no second release spelling, and no head-only wake spelling remaining beside the scan.

## Out of Scope

- Any change to the configured cap values themselves, duplicate rejection, cancellable wait, single-waiter eviction, the scope-exit owner guard, same-identity policy, settle-first ordering, retry budget, void policy, cancellation, timeout/expiry, capability matching, the Deadline race, or the registry wait.
- Evicting holders on lower (tightening never preempts admitted holds; it only stops new admissions until drain brings usage under the cap).
- Priority-aware slot admission (priority still lives in the Tasks dequeue order, not in slot wake order).
- Redefining drained, moving reap off the read path, or naming a new reap seam — all owned by the reap/settle owner and the drain owner, consumed here, never duplicated.
- Moving or reshaping the lifecycle table, the order index, the outcome decision, the Lease shape, or the hold keying.
- Touching the state database, capability registry, Bridge translators and delivery, time adapters and advance policy, generations beyond the preserved reconfigure threading, the package manifest, or any new public interface or observation seam.

## Further Notes

- Dependency: **blocked-by D1 (hard, external)** — the explicit reap/settle owner delivering explicit reap/settle points with reconfigure shape preserved. This work hooks its wake into that explicit point and must not land before it: wiring the consideration into the old getter-triggered reap would bake in the read-that-writes crossing D1 exists to remove and guarantee a rebase. **Transitive edge on D4 (external via D1)** — the pump/drain owner delivering the drain notification hook; this work consumes normal activation traffic only and needs no pump change, but its woken-waiter cascade (refusal returns slot, re-scan, activation) must land on the coalesced pump D4 defines, so it follows D1 which follows D4. Every ticket records both edges.
- Self-grill verdict (autonomous self-grill; decided, no questions asked):
  - D3-Q1 Shared consideration vs separate limit scan? Adopted shared. One scan-plus-install-plus-batch-resume path crossed by both release and limit change: same capacity check, same install, same outside-lock resume, one audit site. A separate scan duplicates all three and reopens two-copy drift (fix lands in one, misses the other) for zero gain.
  - D3-Q2 Wake on raise only vs any limit change? Adopted any-change-triggers, admission-decides. The limit entry always runs the shared consideration; the atomic install gates admission against the new caps so lowers and shrunk axes naturally admit none. Raise-only needs old-vs-new comparison across two nil-means-unbounded caps plus mixed-axis math; reconfigure is rare and the scan is queue-linear, so the comparison buys nothing and adds branches plus tests.
  - D3-Q3 Slot-self-wakes vs reconfigure-pumps-Tasks? Adopted slot-self-wakes. Consideration plus batch resume live inside the slot domain under the controller lock; reconfigure only threads caps and keeps append-plus-reap shape. Pumping Tasks from reconfigure splits admission across modules, nests the generations lock across activation against the single-crossing rule, and duplicates the scan beside scoped-hold ownership.
  - D3-Q4 Explicit-point hook vs getter-triggered wake? Adopted explicit point (hence the D1 hard blocker). Getter-triggered consideration reintroduces the read-that-writes crossing with unnamed lock nesting; the wake must be reachable only via the named reconfigure/settle entries.
  - D3-Q5 Wake budget per limit change: single wake vs admit-every-fitting? Adopted admit-every-fitting bounded by new headroom (global headroom when a global cap binds, per-capability headroom otherwise). One raise can free several disjoint per-capability slots with no global binder; single-wake serializes disjoint demands for no fairness gain. Never-overshoot holds via the atomic install under one lock hold, same as the release drain.
  - D3-Q6 Batch resume inside vs outside the lock? Adopted outside as an arrival-ordered batch on both wake sources, extending the existing release rule; resuming continuations under the controller lock risks re-entrancy into park/cancel.
  - D3-Q7 Refused-at-gate cascade needs a special path? No: refusal exits the hold scope, the single scope-exit release runs the next scan. Pinned by test, not by mechanism.
  - Rejected: wake-then-contend (churns continuations for unreserved capacity), relaxing newcomer no-overtake for limit wake (reopens queue-jumping through the other door), overtake counter or starvation bound (scan-from-head plus reconsideration on every consideration already delays-but-never-strands; a counter adds interface for zero gain), preempting holders on lower (eviction by reconfigure; admission control only).
