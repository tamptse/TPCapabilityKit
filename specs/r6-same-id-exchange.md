## Problem Statement

Same-id rescheduling reads as four crossings across two locks with the ordering argued in prose: look up the non-terminal row for the id, settle the displaced lease as expired, evict its stale slot waiter, then insert the new pending row. Each step releases the scheduler lock, so between lookup and insert another thread can observe a half-displaced id — the new row not yet present while the old lease is already settling, or the old row still present while the new lease already exists. The schedule-waiter identity guard exists precisely to survive that window. The settled-then-evicted-then-inserted order is load-bearing for the stale-evict contract, yet it is enforced by caller discipline across hops rather than by one transition: the table owns rows, order, and counts, the slot controller owns queued waiters, and the enqueue flow owns the ordering comment — three places for one replace.

## Solution

Add a single table-owned exchange transition for same-id replace: displace-old plus insert-new atomically under the one scheduler lock, keeping the settled-then-evicted-then-inserted observable order the slot contract mandates but moving the row atomicity inside. The enqueue flow calls one seam; the slot evict stays a separate lock step after (lock order preserved, never nested). The displaced lease terminalizes through the existing single terminal decision with exactly-once waiter delivery and waiter-task cancellation; the new row starts pending with only its own completion waiters. No Lease shape change. No behavior change except the TOCTOU window closes: lookup-then-insert can no longer disagree.

## User Stories

1. As a Tasks maintainer, I want one exchange seam for same-id replace, so that I stop auditing lookup plus settle plus evict plus insert across two locks to answer one replace question.
2. As a concurrent scheduler, I want no half-displaced id window, so that a lookup between displace and insert never sees a stale row or a missing row.
3. As a displaced lease, I want exactly-once terminal delivery with waiter preservation, so that schedule-and-wait holders of the old lease resume with expiry rather than hanging or joining the new lease.
4. As a new lease, I want a clean pending row with only my own completion waiters, so that the old lease's waiters never leak into my delivery list.
5. As a slot operator, I want stale-evict-after-settle preserved with the same owner-scoped match, so that the new lease's queued waiter survives while the old lease's stale waiter is removed and resume semantics stay false for already-terminal leases.
6. As a schedule-waiter, I want the identity guard to remain as a safety net rather than the primary correctness mechanism, so that a mismatched row still provably means my lease already settled.
7. As a priority scheduler, I want order and counts to agree through the exchange, so that pending plus parked plus active snapshot exactly as today with the old place removed and the new pending added.
8. As a cancel caller, I want cancel-before-exchange and cancel-after-exchange to both land on the right lease, so that no cancel is lost across the atomic swap.
9. As a retry integrator, I want retry re-queue through the same Lease identity untouched, so that completions and live Bridge views survive a retry exactly as today.
10. As a park reviewer, I want park state of the displaced row (waiting flag plus waiter task) taken and cancelled as part of the exchange, so that no parked waiter strands when its row is displaced.
11. As a test author, I want displacement proven by behavior through the public schedule/cancel/wait seam, so that the exchange is verified by outcomes not by transition spelling — except one mechanical grep proving the standalone lookup-then-later-insert path is gone from the enqueue flow.
12. As a future contributor, I want one exchange entry to call instead of four, so that no second displace protocol can be re-introduced by a new path.
13. As an ADR reader, I want the change traceable to single-settlement, unified-lifecycle-ownership, single scoped-hold, and same-id policy decisions, so that the exchange clearly respects prior decisions rather than reopening them.

## Implementation Decisions

- **Module**: Tasks remains the deep module behind the schedule/cancel/pending/active seam. The lifecycle table gains one exchange transition (old id in, displaced delivery payload plus new pending row out); the enqueue flow keeps schedule/displace/evict/insert as the only flow reader. No new module is introduced.
- **Interface**: the public scheduling seam is unchanged (schedule/schedule-and-wait/cancel/pending/active plus result rendezvous). The internal change is lookup plus insert collapse into one table-owned exchange: the caller passes the new lease with its execution and completion waiters, the table atomically displaces any non-terminal row for the same id and inserts the new pending row, returning the displaced lease with its waiters and waiter task for settlement outside the lock.
- **Settlement ownership**: the single terminal decision stays the only decider. The exchange terminalizes the displaced Lease together with its row removal inside the one locked transition (Lease mutation plus row write together, per single-writer discipline) and returns the delivery payload; the caller delivers waiters, cancels the waiter task, and releases via the existing scope-exit path outside the lock. No second terminal path is introduced; the cancelled-to-expired mapping for displacement stays in settlement.
- **Evict ordering**: settled-then-evicted-then-inserted observable order is preserved as (settled-plus-inserted atomically)-then-evicted. The slot evict stays after the exchange under its own lock with the same owner-scoped stale match keyed by the new lease identity, so the new waiter survives and the stale waiter is removed with resume-false on already-terminal leases. Lock order is never nested: scheduler lock, then slot lock, never the reverse.
- **Park interplay**: lands after the park single-seam work and reuses its vocabulary. If the displaced row was parked (waiting flag plus waiter task set), the exchange takes both as part of the displaced payload and cancels exactly once outside the lock; wake-clear versus terminal-take cannot double-clear because take removes the row. Dequeue-to-parked placement is otherwise untouched.
- **Order and counts**: the exchange removes the old id from order and moves its place to removed, then enqueues the new id at its priority and moves nil to pending, so the immutable snapshot agrees exactly as the sequential path produced. Terminal rows need no settle: sequential reuse after terminal inserts without a displaced payload, identical to today.
- **Depth**: depth decreases by three caller-visible steps (four crossings to one table crossing plus one slot step). No new abstraction is added; the exchange is the same row write plus Lease liveness check already owned by the table, with the insert moved adjacent, not a new displace layer.
- **Seam**: the highest seam stays the Tasks schedule/cancel/pending/active facade plus the single result rendezvous and the registry whole-set wait. Tests cross that seam; no new seam is created. The lifecycle table remains the single writer.
- **Expand–contract**: add the exchange beside the existing lookup plus insert methods, migrate the single enqueue caller, then delete the standalone lookup-then-later-insert path from the caller (keeping the underlying row primitives only where other flows still need them). CI stays green batch to batch because the old form still exists until the migrate ticket lands.
- **Lock discipline**: the exchange holds the one scheduler lock once and never nests. Slot evict, waiter delivery, waiter-task cancellation, expiry race, registry wait, and slot hold stay outside the locked section exactly as today.
- **Locality**: displace plus insert plus order plus counts share one reviewable block with the single transition, so the same-id policy needs no hop into the caller comment to audit.
- **Leverage**: leverage is window closure plus drift removal: one crossing to audit, one owner of row replacement, zero caller-side ordering comment to keep in sync. Risk is bounded because the move is spelling-plus-ordering only — same rows, same places, same snapshot derivation, same waiter identity — only the interleaving window closes.
- **Respects ADRs**: single-settlement path constrains the displaced outcome to expired with exactly-once delivery plus waiter preservation and scope-exit release untouched; unified lifecycle ownership requires the table (not the caller) to own the row transition plus waiter lifetime; single scoped-hold discipline forbids moving slot admission or release into the exchange; same-id unsupported policy stays (displacement settles old, new takes id; sequential reuse after terminal keeps working).

## Testing Decisions

- A good test crosses the public Tasks seam and asserts externally observable behavior (concurrent same-id schedules displace exactly once with old waiters delivered expired and new lease pending; sequential reuse after terminal inserts cleanly; stale slot waiter evicted with new waiter surviving; order and counts agree; cancel before versus after exchange lands on the right lease; parked displacement cancels the waiter exactly once), never the spelling of the exchange seam — except one mechanical grep proving no caller-side lookup-then-later-insert protocol remains in the enqueue flow.
- Modules under test: lifecycle table exchange transition (non-terminal displaced with payload versus terminal-or-missing with no payload, order plus counts agreement, parked payload taken), enqueue flow (displace-then-evict-then-deliver order, identity-guard safety net intact, retry identity preserved).
- Prior art: same-id suites (displacement settles old expired, waiter exactly-once, sequential reuse after terminal), lifecycle suites (terminal removal plus counts, double-park plus cancel-while-parked), path locality proof (park/wait/cancel/retry single-delivery plus freed slot), determinism suites (virtual-time timeout, cancel-pins-expired, priority high-before-low, slot serialization), slot-hold suites (admission refusal, FIFO wake, cancellable wait). The exchange must keep every one green with zero test-semantics edits.
- Verification per ticket: `swift build` green plus full `swift test` green; grep proves the old standalone lookup-plus-later-insert caller protocol shrinks monotonically (present beside the new seam after fuse, absent after migrate, unreferenced after pin).

## Out of Scope

- Any change to lifecycle reachability (which states are legal from pending vs parked vs active), priority ordering, retry budget or void-completion policy, waiter preservation or exactly-once delivery semantics, slot limits or release ownership (stays with activation scope-exit), expiry resolution (task timeout vs configured default), or time adapters.
- Changing the public Lease shape, the Bridge live-view reflection, State creation/observation, registry emission order or lock discipline, generation prune or shared-slot coupling, or deterministic-time spelling.
- Touching the slot evict primitive itself, Deadline internals, the registry wait implementation, or the activation gate beyond its existing call site.
- Reopening single-settlement, unified-lifecycle-ownership, scoped-hold, or same-id policy decisions: no revisit trigger is met; the exchange extends them to replace atomicity, it does not redesign them.
- Reformatting or renames beyond the exchange.
