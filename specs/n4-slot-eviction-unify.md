## Problem Statement

Two slot-evict paths in the controller are one primitive spelled twice: `retire(taskId:owner:)` (internal, Tasks displacement) removes the queued waiter under `taskId` whose owner differs from the newcomer, while `cancel(_:)` (private, cancellable wait) removes the parked waiter under the same task id whose owner matches the cancelling Lease. Both are ~8 lines of identical shape — lock, `firstIndex(where:)`, `remove(at:)`, capture resume, resume-false outside the lock — differing only in the predicate (`owner !=` vs `owner ==`). A reviewer asking "how does a queued waiter leave the slots?" must hold two seams to answer one question, and each seam is a drift risk: a future fix to resume-outside-lock, first-only eviction, or false-resume lands in one copy and silently misses the other. The split is shallow (a seam per caller) rather than deep (one mechanism, two intents). Beside it sits a second shallowness: `canAcquire(keys:)` plus `installHold(keys:taskId:owner:)` are two lock-internal steps with a comment-level contract ("callers hold `lock` and checked `canAcquire` first") that both `park` and `release` must honor independently — a check-then-act pair where a future caller can install without checking or check without holding, and the bug hides in the caller, not in the slot module. The same-id policy itself (concurrent reuse unsupported, displaced Lease settles as expired first) already lives in Tasks per the C4 unify; only the eviction mechanism plus the `ObjectIdentifier` threading lives in slots, where `retire` is the deliberate newcomer-keyed exception to Lease-keyed hold.

## Solution

Fuse `retire` plus `cancel` into one waiter-eviction primitive owned by the slot module, and fuse `canAcquire` plus `installHold` into one atomic install. The controller exposes a single `removeWaiter(taskId:owner:match:)`-shaped primitive (exact name at implementation time; an `evictWaiter` with predicate spelling is equivalent) where the two callers name intent, not predicate: displacement evicts stale (owner differs), cancellation evicts self (owner matches). The primitive keeps the slot-only contract both copies already honor: evict at most one queued waiter, resume it with false outside the lock, touch no Lease, no row, no lifecycle transition. `withHold` stays the sole admission seam untouched; `park` keeps admission plus FIFO order plus cancellable wait, `release` keeps the scope-exit guard plus head-wake, both calling the same eviction and install primitives. `canAcquire` plus `installHold` become one lock-internal atomic `tryInstall` (check-and-install in one step returning admitted/not): `park` and `release` no longer spell check-then-install as two calls, so the hold-lock-plus-checked-first obligation stops living in callers. No behavior change: stale-eviction, self-cancel, self-retire no-op, cancel-never-yanks-another-holder, FIFO wake, scope-exit release, and the Tasks settle-first ordering are identical before and after. N1 (lease-terminal unify) is recommended first: it moves the settle step this displacement path orders against, so landing N1 first keeps the settle-then-retire ordering onto a stable site — advisory sequencing, not a hard blocker.

## User Stories

1. As a Tasks maintainer, I want one waiter-eviction primitive instead of two predicate-flipped copies, so that resume-outside-lock and first-only eviction review in a single hop.
2. As a displacement reviewer, I want the enqueue settle-then-retire-then-insert path to call an evict-stale intent, so that the call site states policy while the controller owns mechanism.
3. As a cancel caller, I want cancel-while-waiting to call an evict-self intent through the same primitive, so that owner-mismatch no-ops (never yanks another holder's wait) without a second copy to audit.
4. As a slot reviewer, I want stale-evict and self-cancel to share one resume-false-outside-lock shape, so that a future eviction fix cannot land in one copy and miss the other.
5. As a `park` caller, I want admission to read as one atomic try-install (checked-and-installed in one step), so that no future park edit can install without checking or check without holding the lock.
6. As a `release` reviewer, I want head-wake to use the same atomic try-install as `park`, so that check-then-act cannot drift between the two admission sites.
7. As a `withHold` consumer, I want the sole admission seam unchanged, so that admission, FIFO wake order, cancellable wait, and scope-exit release promises survive the fuse untouched.
8. As a same-id reuser, I want concurrent overwrite to keep expiring the old Lease exactly once before eviction, so that the resume-false still lands on an already-terminal Lease (settle-first preserved).
9. As a sequential reuser, I want reuse after terminal to keep working untouched, so that id lifecycle semantics are unchanged by the mechanism merge.
10. As a FIFO waiter, I want wake order and first-only eviction identical, so that fairness promises survive the fuse.
11. As a test author, I want displacement covered once through the scheduling facade, so that no test pins which half of the old duplication evicted which waiter.
12. As a test author, I want the narrow evict contract pinned directly with intent-level cases (stale evicted, self cancelled, self-retire no-ops, stranger untouched, admitted holder unaffected), so that the fused primitive is explicit without re-pinning policy below the facade.
13. As a reviewer, I want the full existing suite green with no behavior change, so that this refactor is provably semantics-preserving.
14. As a future contributor, I want one obvious eviction primitive plus one obvious install primitive, so that new paths cannot grow a third predicate copy or a bare `installHold` without a check.
15. As an ADR reader, I want the change traceable to scoped-hold ownership, Lease-keyed hold with the retire exception, and task-keyed same-id policy, so that the fuse clearly respects prior decisions rather than reopening them.

## Implementation Decisions

- **Module**: the slot controller remains the slot module owning admission, FIFO wake order, cancellable wait, scope-exit release, plus waiter eviction as pure mechanism. Tasks keeps owning the same-id policy end to end (settle displaced as expired first, then evict, then insert). No Lease or row logic moves into the controller; no new module is introduced.
- **Interface**: one eviction primitive replaces two seams (`retire` internal plus `cancel` private). Shape: task id plus owner plus a match intent (stale vs self; a predicate/closure spelling is equivalent) — callers name intent, the controller applies the predicate internally under its lock. `cancel`'s Lease-keyed entry shape may stay as a thin intent wrapper if callers read better that way; the duplication (lock/index/remove/resume) exists exactly once. The rejected alternative (keep two seams and extract only a shared remove-at-index helper) preserves the seam-per-caller shallowness this candidate exists to close.
- **Depth**: depth decreases by one seam and one check-then-act pair. No new abstraction is added; the fused evict plus the atomic install are the same locked steps with the predicate and the check moved inside, not new layers.
- **Seam**: the highest seam stays the scheduling facade (schedule/schedule-and-wait/cancel/pending/active) plus `withHold` as the sole admission seam. Tests pin displacement at the facade; the fused evict is the single cross-module eviction seam Tasks crosses, slot-only by construction (resumes a continuation, touches no Lease, crosses no lifecycle transition).
- **Adapter**: no adapter change. The Bridge stays the single ObjC scheduling adapter and is untouched; eviction is invisible from Objective-C.
- **Locality**: predicate (`owner !=` for stale, `owner ==` for self), first-only removal, false-resume-outside-lock, and the self-retire/stranger no-op rules read adjacent inside one primitive, so the full eviction contract needs no hop. Check-plus-install reads as one atomic step, so admission needs no caller-side discipline comment.
- **Leverage**: leverage is copy-removal plus caller-proofing: one eviction shape to fix, one install to audit, zero cross-copy sync, zero comment-contract callers. Blast radius is bounded because both current copies already share the exact lock/index/remove/resume-outside shape and both install sites already hold the lock and check first — the fuse only moves the shared shape inside.
- **Owner choice**: the controller owns the fused primitive because eviction is mechanism (queue search plus continuation resume) with no lifecycle visibility; Tasks owns when to call it (displacement intent) as today. The `ObjectIdentifier` threading through `retire` stays: it is the named newcomer-keyed exception to Lease-keyed hold, not a second token spelling.
- **Ordering**: enqueue keeps settle-then-retire-then-insert, each step outside the other's lock, never nested, per the Store-to-Tasks lock-order contract. Settle-first stays load-bearing (resume-false lands on an already-terminal Lease). The fuse changes neither order nor lock discipline.
- **N1 sequencing**: N1 (lease-terminal unify) is recommended first because it fuses the decide-then-transition settle step this path orders against. N4 applies cleanly after; applying before N1 is possible but rebases the ordering comments onto a moving settle site. Recorded as advisory, encoded in the first ticket, not as a lock-order or correctness dependency.
- **Respects ADRs**: ADR-0013 (controller owns admission, FIFO wake, cancellable wait, scope-exit release behind one scoped-hold seam — the fuse stays inside that ownership, `withHold` untouched); ADR-0018 (single scoped-hold seam — no second admission spelling is added); ADR-0019 (hold is Lease-keyed with retire as the deliberate newcomer-keyed exception — the fused primitive preserves the exception rather than re-tokenizing); ADR-0006 (task-keyed slot ownership with controller-owned idempotent release — eviction touches only queued waiters, never held entries); ADR-0011 (same-id concurrent scheduling unsupported; overwrite settles old as expired before the new row takes the id — Tasks policy ownership and settle-first ordering preserved).

## Testing Decisions

- A good test pins externally observable behavior through the scheduling facade (overwrite expires old exactly once, sequential reuse works, FIFO order preserved, cancel-while-waiting strands nothing) plus intent-level pins of the fused primitive at the controller seam (stale evicted with false, self cancelled with false, self-retire no-ops, stranger waiter untouched, admitted holder unaffected, atomic install admits only when capacity allows) — never which pre-fuse copy evicted which waiter.
- Modules under test: the enqueue displacement path (settle-first ordering through the facade), the fused eviction primitive (both intents plus all no-op guards), and the atomic install (park admission, release head-wake, double-acquire still rejected).
- Prior art: the settlement overwrite test (old-expired-once plus new-completes through the facade), the sequential-reuse test, the narrow retire test, and the controller slot-hold suite (double-acquire rejection, FIFO, cancel-while-waiting) are the models — all stay green with zero test-semantics edits; intent-level evict cases extend the narrow retire pin rather than re-pinning policy below the facade.
- Verification: focused settlement plus slot suites first, then the full suite green; grep confirms no production or test caller depends on the removed two-copy spelling (`retire(` as a separate seam from self-cancel removal, bare `installHold` without the atomic wrapper, or `canAcquire`-then-`installHold` spelled at call sites).

## Out of Scope

- Any semantic change to admission limits, FIFO wake order, cancellable wait, scope-exit release guard, same-id unsupported policy, expired-settle-first ordering, retry budget, void policy, cancellation, timeout/expiry, capability matching, or sequential same-id reuse.
- Moving or reshaping the lifecycle table, the order index, the outcome decision, the Deadline race, the registry wait seam, or the Lease-keyed hold spelling.
- Touching the state database, capability registry, Bridge translators and delivery, time adapters and advance policy, generations, the domain glossary, decision records beyond a new ADR entry, or package manifest.
- Introducing new observation or waiting seams, new validated types, or any new public interface beyond the fused internal primitives.
- The N1 terminal-vocabulary unify itself — sequenced before, not folded in.

## Further Notes

Grill record (autonomous self-grill, two rounds; all open questions delegated to coordinator, recommendations adopted):

- Round 1, Q1 — Fuse shape: one `removeWaiter` with match intent vs one shared remove-at-index helper under two seams? Fused primitive: the helper-only split keeps seam-per-caller shallowness (two predicates, two resume sites to drift). Intent-naming (stale vs self) keeps call sites readable while the mechanism exists once. Adopted.
- Round 1, Q2 — Does `cancel` stay Lease-keyed while `retire` stays newcomer-keyed inside one primitive? Yes: the keys name different holders by necessity (self vs newcomer). Forcing one key shape would either hide the task-id keying the stale case exists to name or force Tasks to name stale state it may not hold. The primitive accepts both; ADR-0019 exception preserved. Adopted.
- Round 1, Q3 — Atomic install now or separate candidate? Now, same ticket pair: it is the same shallowness class (comment-contract check-then-act) in the same file on the same lock, and leaving a bare `installHold` beside a fused evict invites the next caller to bypass the check. Small enough to ride along. Adopted.
- Round 1, Q4 — N1 dependency: hard blocker or advisory? Advisory (recommended first): N1 moves the settle site this path orders against, so sequencing avoids rebase churn, but neither correctness nor lock order depends on N1 landing first. Encoded as a sequencing note on ticket 01, not a blocked-by edge. Adopted.
- Round 2 (Strong deepening), Q5 — Evict-more-than-one? No: both current copies evict first-only; FIFO fairness plus exactly-once resume depend on single eviction. A bulk-evict spelling would reopen stranded-vs-double-resume reasoning. Single-eviction preserved. Adopted.
- Round 2, Q6 — Does the release scope-exit owner check merge into the fused evict? No: it guards held entries (slot theft), not queued waiters (eviction). Merging would conflate held-vs-queued ownership and reopen the displaced-active self-heal the guard closed. Untouched. Adopted.
- Round 2, Q7 — Resume inside vs outside the lock after fuse? Outside, as both copies already do: resuming a continuation under the controller lock risks re-entrancy into park/release. The fuse preserves outside-lock resume as part of the single shape. Adopted.
- Round 2, Q8 — Test split: extend narrow retire pin vs new evict suite? Extend: the narrow retire test already pins evict-stale at the controller seam; adding self-cancel plus no-op intents to the same pin keeps one mechanism suite instead of two. Facade tests untouched. Adopted.

Strong recommendation holds after both rounds: two predicate-flipped copies plus a comment-contract check-then-act are strictly riskier than one intent-named evict plus one atomic install, and the shared lock/index/remove/resume shape makes the fuse mechanical with facade-level verification.
