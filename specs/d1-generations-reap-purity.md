## Problem Statement

A maintainer asking "what does reading a count do?" still gets a read that writes: every count read (pending, active, generation count) routes through one generations snapshot whose first step reaps drained generations by mutating the generations list and asking each non-current generation for its drain state. The parent hardening gave that prune one name, one stated Store-to-Tasks crossing, and one lock-safe copy-check-sweep shape — but the trigger point is still the read path itself. Each getter therefore carries hidden write semantics: auditing a count means auditing mutation-safety, auditing the lock crossing, and re-proving the flag-then-sweep safety argument per read. Any future settle-driven lifecycle (a pump that knows when a generation goes drain-stable) has a named pass to call but no explicit call site to call it from — the only caller is the getter. Counts are correct; the read path is impure.

## Solution

Move generations reaping off the count-read path to explicit reconfigure and settle points fed by a settle/drain notification owned by the pump lifecycle. Getters become pure reads: copy the generation list under the scheduling lock, sum the per-generation counts, report how many generations are currently held — asking no drain state, mutating nothing. The named reap pass is reused verbatim (copy under lock, ask drain state with no scheduling lock held, sweep under lock removing only still-present non-current generations flagged drained) and is now reachable only from the explicit points: the existing reconfigure append-plus-reap and a new settle-triggered reap entry that the pump's settle/drain notification calls. No drain redefinition, no slot-domain change, no gate change: same summed counts at every explicit point, same shared slot admission, same current-never-reaped rule, same precede-first-use gate reading the same numbers through the now-pure view. The accepted semantic delta is transient staleness by design: a generation that drains stays visible in counts until the next explicit reap releases it, instead of vanishing on the next getter. Deletion test: deleting the reap call from the read path (getters read only the pure view) changes steady-state counts at explicit points not at all and changes between-point counts only by the documented linger-then-release.

## Implementation Decisions

- **Module**: the Store scheduling-generations module keeps its shape (generation list, shared slots, shared clock behind the scheduling facade). Only the reap trigger relocates: the read path loses its reap call and the explicit points gain it. No new module is introduced.
- **Interface**: the public scheduling seam is unchanged (schedule, schedule-and-wait, cancel, pending, active, configure, plus the internal generation-count and deterministic-time controls). The internal change is the snapshot view splits into a pure read (lock, copy, sum, report) feeding all getters and the unchanged named reap pass feeding only reconfigure and the settle entry. The settle/drain notification is consumed as a caller of the settle entry, not designed here.
- **Reap shape reused verbatim**: copy-check-sweep — copy the generation list under the scheduling lock, ask each non-current generation for drain state with no scheduling lock held, re-acquire and remove only generations still present, still non-current, and flagged drained. The current generation is never reaped even if drained. No re-check of drain state under the sweep lock, on the invariant D4 re-proves.
- **Why no re-check under lock**: non-current generations drain monotonically — new work lands only on the current generation, cancel only removes, retry re-queues within its own generation — so a generation flagged drained cannot become live again before the sweep. This invariant is consumed here as re-proven by D4 under coalesced pumping; this work neither re-proves nor weakens it.
- **Drain definition untouched**: drained still means empty pending plus active from one scheduler acquisition. Redefining it belongs to the pump owner; this work moves when the question is asked (explicit points only) without changing the question.
- **Explicit points**: exactly two — the existing reconfigure append-plus-reap and the settle-triggered reap entry fed by the settle/drain notification. Getters, cancel, and the deterministic-time controls never trigger a reap. Decision-encoding state shape: the pure view reports (pending sum, active sum, held-generation count) over the currently held list with no release applied.
- **Notification discipline**: the settle entry is idempotent (reaping an already-reaped list is a no-op) so duplicate or coalesced notifications are safe; the entry performs the named pass and nothing else — no admission, no parking, no settlement work moves into it. Pump internals (single kick entry, drain loop, missed-wakeup guard) are D4's design and are not restated here beyond the consumed contract.
- **Lock discipline**: the pure view holds the scheduling lock once for copy-and-sum and never crosses into Tasks; the named pass remains the single allowed Store-to-Tasks crossing, stated once at the pass. Everywhere else the header discipline stands: no caller holds the scheduling lock across a submodule call.
- **Seam**: the highest seam stays the Store scheduling facade plus the internal generation-count and deterministic-time controls. Tests cross that seam; no new seam is created. The settle entry is internal mechanics beside the named pass, reachable from the pump notification after D4.
- **Expand–contract**: the pure view and the settle-triggered entry land beside the current reaping snapshot (mechanical, independently reviewable), explicit-point behavior is pinned while getters still reap, then the read-path reap call is deleted. Each ticket lands green because no ticket changes reachability, ordering, admission, or delivery — only where release is triggered.
- **Transient staleness is intended**: between explicit points, counts sum across held generations including drained-but-not-yet-released ones, so generation count may read transiently higher than under getter-triggered reaping. Steady-state values at explicit points are identical; pins that previously relied on getter-triggered release drive an explicit point instead.
- **Depth**: depth increases by removing one hidden protocol (every read was secretly a reap trigger) with no new abstraction added — one pure view for callers, one named pass for two explicit callers. **Leverage** is read-path audit locality plus contention removal: counts need no drain reasoning, drain checks leave the hot read path. **Locality** is release-timing knowledge concentrating at two explicit points instead of spreading across every getter.
- **Respects ADRs**: generations ownership requires counts to keep summing across live generations with in-flight preservation; slot-sharing requires admission to stay on the one Store-owned domain so the limit never doubles during drain; lock-order requires the reap pass to stay the single Store-to-Tasks crossing with drain checks outside the scheduling lock; deterministic-time spelling keeps the precede-first-use gate reading the same numbers. None are reopened.

## Testing Decisions

- A good test crosses the public Store scheduling seam and asserts externally observable behavior (pending/active sums across live generations under one shared limit, drained release after an explicit point, reconfigure preserving in-flight work, precede-first-use gate behavior, linger-then-release between points), never the spelling of the pure view or the reap pass — except mechanical greps proving the read path asks no drain state and mutates nothing, and the Store-to-Tasks crossing exists only at the named pass.
- Modules under test: pure view (repeated reads change nothing: generation count stable across back-to-back reads with no explicit reap), explicit points (reconfigure append-plus-reap with in-flight preservation; settle-triggered entry releases a drained non-current generation and is idempotent; current-never-reaped through the settle entry), sums (pending/active aggregate across two live generations including a drained-but-unreleased one), deterministic-time gate (unchanged precede-first-use meaning through the pure view), cancel fan-out (unchanged).
- Prior art: generations wiring suites (drain triple sums pending while sharing admission, pending sums across generations), snapshot postcondition suites (drain sums counts under one shared limit with unforked virtual time), generations suites (in-flight preservation with aggregated counts and drained release), shared-slot-domain suites, store determinism suites. The flip keeps every one green with semantics edits confined to driving an explicit reap where a pin previously relied on getter-triggered release; no limit, ordering, delivery, or expiry semantics may change to accommodate the flip.
- Verification per ticket: `swift build` green plus full `swift test` green; grep proves the relocation moves monotonically (read-path drain-state reads present before, absent after; explicit settle entry absent before, present after; exactly two reap call sites after).

## Out of Scope

- Any change to what counts as drained, to priority ordering, retry budget or void-completion policy, waiter preservation or exactly-once delivery, slot limits or release ownership, expiry resolution, or time adapters.
- Designing the pump internals (single kick entry, drain loop, missed-wakeup guard, per-generation flag scope): owned by D4 pump single-drain-owner and consumed here only as the notification contract plus the re-proven invariant.
- Changing the public Lease shape, the Bridge live-view reflection, State creation/observation, registry emission order or lock discipline, or deterministic-time spelling.
- Touching the slot admission primitive itself, Deadline internals, the registry wait implementation, or the activation gate.
- Reopening generations-snapshot, slot-sharing, lock-order, unified-lifecycle-ownership, or single park-seam decisions: no revisit trigger is met; the purity move extends them, it does not redesign them.
- Polling or timer-driven reaping as a substitute for the settle notification; reformatting or renames beyond the trigger relocation.

## Further Notes

- Dependency: **blocked-by D4 pump single-drain-owner (flip only)**. Early tickets land without D4: they add the pure view and the settle-triggered entry beside the current reaping snapshot with zero behavior change and invent no pump internals. The final flip requires D4 first because only D4 can say when a generation is drain-stable under coalesced pumping and can feed the Store the settle/drain notification so a drained generation releases without a getter triggering the reap. Tickets record the D4 contract as (a) one reviewable pump drain lifecycle with a single kick entry, (b) a settle/drain notification callable from reconfigure/settle points, (c) the re-proven non-current-generations-drain-monotonically invariant under coalesced pumping. Tickets record this as a sequencing note on the mechanical work and a hard blocked-by edge on the flip.
- Self-grill verdict (autonomous self-grill; decided, no questions asked):
  - D1-Q1 Pure reads now versus explicit-points first? Adopted explicit-points first inside this candidate: land the pure spelling and the settle entry beside the reaping snapshot while getters still reap, then flip. Flipping without the settle entry would strand drained generations until the next reconfigure with no trigger to release them — the suites pinning generation-count-returns-to-one after natural drain would fail.
  - D1-Q2 Reuse the sweep verbatim versus redesign it for settle timing? Adopted reuse verbatim. The copy-check-sweep with flag trust plus presence/current re-check is the reviewed shape; redesigning it here would fork the invariant D4 must re-prove and force a rebase in both directions.
  - D1-Q3 Accept transient staleness versus preserve getter-triggered freshness? Adopted transient staleness as intended semantics. Freshness-on-read is exactly the impurity being removed; the replacement guarantee is convergence at explicit points, pinned by linger-then-release tests.
  - D1-Q4 Design the notification versus consume it? Adopted consume-only. Any notification shape invented here risks contradicting D4's single kick entry and drain loop; this candidate defines only the receiving entry (idempotent reap, nothing else) and records D4's three deliverables as the hard edge.
  - D1-Q5 Polling fallback if the notification is late? Adopted no polling. A timer reintroduces an anonymous trigger with its own ordering and lifetime questions and undermines the two-explicit-points reviewability; if the notification is absent the flip waits on D4.
  - D1-Q6 Re-check drain under the sweep lock now that timing moved? Adopted no. Re-checking under lock reintroduces the nesting the parent removed; safety continues to rest on the monotonic-drain invariant, whose re-proof under coalesced pumping is D4's explicit deliverable.
  - D1-Q7 Two tickets or three? Adopted three (expand, prove-explicit-points, flip-plus-verify) in expand–contract order, so the mechanical addition lands independently reviewable from the explicit-point pins and the D4-gated flip reads as one deletion of the read-path reap.
  - Rejected: redefining drained (belongs to D4), preserving getter-triggered reaping as a backstop after the flip (keeps the impurity and double-trigger ambiguity), fusing slot admission into the reap (nests lock domains), adding a generations delegate protocol (leverage ~nil), timer-driven reaping (anonymous trigger).
- Deletion test is the acceptance bar: deleting the reap call from the read path (getters read only the pure view) changes steady-state counts at explicit points not at all and changes between-point counts only by the documented linger-then-release.
