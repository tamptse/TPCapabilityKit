## Problem Statement

The Tasks expiry seam carries `Bool` only (`TaskScheduler+Deadline.swift:23-39 race(operation:) -> Bool`), while the executor needs to carry a result value (`Any?`) through the same expiry. Today's executor smuggles that value around the race via a per-execution `ExecutionBox` (`TaskScheduler+Path.swift:133-142`): a second `NSLock` plus a side-channel slot that is written inside the winning branch and re-read after the race (`TaskScheduler+Path.swift:128-157 runActivatedLease`). The result is a shallow-interface tax plus a second lock domain for one call site: reviewers must audit two locks (the scheduler lock domain plus the box lock) and a `Any??` won-gate to answer "who won the race and with what value", while the CONTEXT glossary already promises one race shared by waiter and executor — today only the expiry instant is shared, the value is not.

## Solution

Generalize the race seam to carry a value: the waiter keeps a `Bool` specialization with identical semantics (timeout maps to `false`), the executor carries its `Any?` result through the race itself as an outer-optional distinguishing timeout (`nil` outer) from stored-nil (`.some(nil)`), and the registry keeps receiving the `Bool` race as an opaque value without ever naming the Tasks expiry type. `ExecutionBox` and its lock are deleted; TaskGroup first-wins plus `cancelAll` owns the exclusion and the loser result is discarded, never stored. Timeout-resolve-once at Deadline construction is untouched. This goes one step beyond `specs/n6-lifecycle-depth.md` (which removes the named type but keeps the `Bool` shape): R4 changes the shape the race can carry, N6 changes the address where the race lives.

## User Stories

1. As a Tasks maintainer, I want waiter and executor to share one value-carrying race, so that I stop auditing a `Bool`-only race plus a side-channel box to answer one expiry question.
2. As a capability waiter, I want the `Bool` wait semantics byte-identical (available resolves `true`, expiry resolves `false`), so that park, expiry, activation, and settlement behave exactly as today.
3. As a scheduled-task caller, I want an executed value delivered when the operation wins and `nil` with expired settlement when the timeout wins, so that completion vs expiry is decided by the race outcome alone.
4. As a void-completion integrator, I want stored-nil (operation produced `nil`) still distinguished from never-stored (timeout won), so that the Settlement retry-vs-fail-vs-expire policy reads the same outcome as before.
5. As a concurrency reviewer, I want the second `NSLock` domain gone, so that exactly-once terminal delivery is auditable from TaskGroup first-wins plus `cancelAll` with no loser-write to reason about.
6. As a registry owner, I want the whole-set wait seam unchanged (`Bool` race received as an opaque value, empty-set and already-satisfied fast paths untouched), so that the registry never names the Tasks expiry type.
7. As a Settlement reviewer, I want the won-gated read preserved (timeout path never consults the value slot), so that a late loser completion cannot leak into an already-expired Lease.
8. As a timeout-contract reader, I want timeout still resolved once at Deadline construction from task plus configured default, so that waiter and executor provably share one deadline.
9. As a test author, I want expiry proven by behavior through the public schedule/cancel/wait seam plus deterministic time, so that the box deletion is verified by outcomes not by holder spelling — except one mechanical grep proving `ExecutionBox` is gone.
10. As a Swift 6 reviewer, I want the value-carrying form to compile under strict concurrency without an unbounded `T: Sendable` generic over `Any?`, so that no new `@unchecked` escape or sendability hole is introduced beyond today's box scope.
11. As an N6 sequencer, I want the Deadline named type kept (resolve-once suite constructs it directly), so that R4's shape change and N6's address collapse never conflict and N6 can land after R4 unchanged.
12. As a future contributor, I want Path to remain the sole flow reader of the race (wait adaptation plus executor call), so that no second race construction site can re-split waiter vs execution expiry.
13. As a slot operator, I want scoped-hold admission, FIFO wake, cancellable wait, and scope-exit release untouched, so that concurrency limits behave identically before and after.
14. As a retry integrator, I want retry re-queue through the same Lease identity preserved, so that completions and live Bridge views survive a retry exactly as today.
15. As an ADR reader, I want the change traceable to one waiter plus injectable clock, Deadline-owned expiry, and registry whole-set wait decisions, so that the generalization clearly respects prior decisions rather than reopening them.

## Implementation Decisions

- **Module**: Tasks remains the deep module behind the schedule/cancel/pending/active seam. The Deadline module keeps owning timeout-once resolution plus the single race; the time module keeps owning live plus virtual adapters and the advance policy behind one sleep seam. No new module is introduced; the value form lives beside the `Bool` form in the same expiry module.
- **Interface**: the race seam gains a value-carrying form for the executor result (`Any?` carried through the race with timeout as `nil` outer vs won as `.some(value)` where value may itself be `nil`), while the waiter keeps the `Bool` specialization (`race(operation:) -> Bool`, timeout maps to `false`, operation-`false` still maps to `false` so waiter outcomes are unchanged). A concrete `Any?` overload pair sharing one private TaskGroup topology is preferred over an unbounded `T: Sendable` generic, because the executor's `Any?` is not `Sendable` and `withTaskGroup(of:)` requires a `Sendable` element — the concrete pair avoids a new sendability escape. If a generic is added for future callers it must be `T: Sendable` only, with the `Any?` path kept as the concrete overload, never forced through the generic bound.
- **Depth**: depth decreases by one nested type plus one lock domain (`ExecutionBox` and its `NSLock` deleted) with zero new abstraction. The race topology (one operation task plus one sleep task, first-wins, `cancelAll`) is stated once and shared by both forms; only the carried payload differs.
- **Seam**: the highest seams stay the Tasks schedule/cancel/pending/active facade plus the single result rendezvous and the registry whole-set wait (`waitForAll` keeps its `Bool`-race value parameter; `DynamicStore.waitForAllCapabilities` keeps its `Bool`-race delegation). Tests cross those seams; no new seam is created. The registry never names the Tasks expiry type — Path adapts the `Bool` specialization into the existing closure value exactly as today.
- **Adapter**: no adapter change. The Bridge live Lease view, ObjC timeout mapping (wire-negative vs explicit plus pinned-compat literal), and time live/virtual adapters plus advance policy are untouched; deterministic-time spelling stays on the facade.
- **Locality**: the won gate stays adjacent to the executor call: timeout yields expired with an empty result without consulting the carried value; won delivers the carried value (including stored `nil`) into the existing `settle(lease,result:timedOut:execution:)` entry. The `stored-nil vs never-stored` distinction moves from box-slot-plus-`won` into outer-optional-plus-`won` with identical truth table; a bare-optional fold without the won gate is rejected.
- **Leverage**: leverage is interface depth plus lock-domain removal: one race topology to audit, one lock domain fewer, zero cross-primitive sync (race outcome vs box slot). Risk is bounded because both forms share the same TaskGroup shape and the same resolved timeout — only the payload path changes.
- **Ordering**: R4 lands before N6-ticket-01 (Deadline collapse). R4 keeps the Deadline named type; N6 deletes or privatizes it afterwards without re-editing the value path. R4 assumes N1 (terminal unify) and N4 (slot-eviction unify) post-state and must not re-split what they fused.
- **Respects ADRs**: ADR-0010 (one waiter with injectable clock; waiter and executor share one expiry deterministically) constrains the change to keep one resolved timeout feeding both paths; ADR-0012 (Deadline owns expiry: resolve-once plus single race for wait and execution) is extended from `Bool`-only to value-carrying, not reopened — resolution site and sharing topology are unchanged; ADR-0024 (registry serves whole-set readiness; Tasks keeps park, expiry, activation, settlement) forbids moving set-matching into Tasks or expiry/settlement into the registry — the registry seam stays `Bool`-only.

## Testing Decisions

- A good test pins externally observable behavior through the public Tasks seam with deterministic time (expired vs completed vs retry, delivered value identity, waiter counts), never the holder type or lock internals — except one mechanical grep proving no `ExecutionBox` reference remains.
- Modules under test: race specialization parity (Bool form: operation-win `true` vs timeout `false` vs operation-`false`; value form: won-with-value vs won-with-stored-nil vs timeout-empty), executor path (`runActivatedLease` delivering race-carried value into Settlement, timeout delivering expired with empty result), registry wait (empty-set true, already-satisfied true, whole-set win vs single-expiry timeout, per-Capability-before-snapshot order untouched).
- Prior art: expiry suites (resolve-once construction, execution-expiry delivery, operation-wins race), single-expiry waiter-plus-executor agreement, timeout-contract shared-expiry across mid-wait flip, registry wait suites, Settlement and Settlement-guards (void-completion retry policy), activation-gate and slot-hold suites. The generalization must keep every one green with zero test-semantics edits except the new value-path additions.
- Per-ticket verification runs the focused suites first, then the full suite: `swift test --filter DeadlineTests`, `swift test --filter SingleExpiryTests`, `swift test --filter TimeoutContractTests`, `swift test --filter CapabilityRegistryWait` (per ticket-03 list), ending with `swift test` for the whole package.

## Out of Scope

- Deleting or privatizing the Deadline named type (N6-ticket-01 owns that address change; R4 keeps the type so the resolve-once suite keeps constructing it directly).
- Any change to timeout resolution (task value vs configured default) or to the pinned-compat timeout fork.
- Any change to the Settlement decision table, retry budget, void policy, or slot-release ownership (stays with activation scope-exit).
- Any change to lifecycle reachability, priority ordering, park double-park or waiter-cancel rules, generation sharing, or State creation/observation.
- Changing the registry wait interface shape, emission order, or lock discipline; generalizing the registry seam beyond `Bool`.
- Splitting the Store facade, introducing a scheduler protocol, adding a lock domain, or any formatting churn beyond the race generalization plus box deletion.

## Further Notes

- Deletion test is the acceptance bar: deleting `ExecutionBox` (callers read only the value-carrying race result) changes nothing observable through the public scheduling seam; `grep -rn ExecutionBox Sources/` must return empty at rest.
- If generic-vs-concrete-overload is contested during implementation, prefer the concrete `Bool` plus `Any?` overload pair sharing one private topology over an unbounded generic, because `Any?` is not `Sendable` and the generic bound cannot carry the executor result without a new escape.
- If outer-optional vs result-enum is contested, prefer the outer-optional (timeout `nil` outer, won `.some(value)`) over a new `RaceResult` enum, because it adds zero named types and the won gate already exists at the settle entry — but either is acceptable iff the stored-nil vs never-stored truth table is preserved and asserted by test.
- Source of prototype decisions: none — no prototype; decisions derive from the `TaskScheduler+Deadline.swift:23-39` plus `TaskScheduler+Path.swift:128-157` inventory, the `CapabilityRegistry.swift:18,123-135` plus `DynamicStore.swift:138-143` seam inventory, and ADRs 0010/0012/0024.

## Grill Record (grill-with-docs, autonomous — no user rounds; strong items auto-deepened)

- Frontier Q1 — Generic `<T: Sendable>` race vs concrete `Bool` + `Any?` overload pair? Verdict: Strong for the concrete pair. `withTaskGroup(of:)` requires a `Sendable` element and the executor result is `Any?` (not `Sendable`); an unbounded generic cannot carry it without a new `@unchecked` escape. Auto-deepened: ticket-01 implements the concrete pair sharing one private topology; an optional future `T: Sendable` generic may only be additive, never the executor path.
- Frontier Q2 — Should the registry `waitForAll` seam generalize beyond `Bool`? Verdict: No (Strong). The waiter only needs win/lose; generalizing the registry would widen the one seam ADR-0024 deliberately narrowed and force the registry to reason about values it never consumes. Auto-deepened: registry keeps the `Bool`-race value parameter; only Path's executor call migrates to the value form.
- Frontier Q3 — Stored-nil vs never-stored collision under a value race? Verdict: Strong load-bearing. A naive `T?`-with-`nil`-means-timeout fold collides for `T = Any?` (operation-produced `nil` vs timeout `nil` both read `nil`). Auto-deepened: the value form returns outer-optional (`nil` outer means timeout, `.some(inner)` means won with `inner` possibly `nil`) AND the settle entry keeps the won gate (timeout never consults the value). Ticket-03 asserts the full truth table including void-completion retry on stored-nil.
- Frontier Q4 — Does TaskGroup first-wins plus `cancelAll` fully replace the box `NSLock`? Verdict: Yes, Worth-exploring upgraded to Strong after C5 evidence. The box lock only mediated winner-write vs post-race-read on a per-execution holder that never escapes; first-wins plus cancellation discards the loser without storing, so there is no shared slot left to guard. No new lock domain is introduced.
- Frontier Q5 — R4 vs N6 ordering (both touch Deadline)? Verdict: Strong sequence R4-then-N6. R4 changes the race shape and keeps the named type (the resolve-once suite constructs `Deadline` directly); N6-ticket-01 changes the address (collapse to Path-private helper) and keeps the `Bool` contract for the waiter. R4 tickets declare the N1+N4 post-state assumption and the N6-follows note so neither re-splits the other.
- Frontier Q6 — One ticket or three? Verdict: three, ordered seam-then-migration-then-proofs, so the value seam lands green beside the box path before the box is deleted, and the proofs ticket can fail without endangering the migration. Ticket-02 is blocked by ticket-01; ticket-03 is blocked by ticket-02.
